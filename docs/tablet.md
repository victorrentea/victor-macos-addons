# Android Tablet Integration (LaunchBreak) & Deploy

Transport to/from the tablet, video playback, auto-deploy (cable or WiFi), and the phone-battery mirror. The tablet→Mac **sound routing** protocol (and everything Bluetooth-speaker/audio) lives in `audio-sounds.md`.

## Tablet ↔ Mac transport (local Wi-Fi preferred, internet last resort)
The tablet reaches the Mac over four transports, first that answers wins (`MacLink.reach`,
tablet side): USB (`localhost:55123` via `adb reverse`) → **the Mac's raw LAN IP `http://<ip>:55123`**
→ mDNS (`Victor-Mac.local:55123`) → the **Railway relay** (`RailwayBridgeClient` ⇄ tablet's
`MacBridge`, `wss://interact.victorrentea.ro`), which is a genuine LAST resort. The `/ping`
response advertises the Mac's own LAN IPv4s as **`macLanIps`** (`NetworkInfo.lanIPv4Addresses()`,
`en*` interfaces) so the tablet — which gets `/ping` even over the relay — can probe the Mac
**directly on the shared Wi-Fi**, sidestepping mDNS (which phone hotspots filter). This is what
stops the tablet falling to the internet relay when both devices are on the same hotspot.
The `TabletHttpServer` `NWListener` already binds all interfaces, and the tablet's
`network_security_config` permits cleartext to those raw IPs (previously only `.local`/localhost,
so the raw-IP path was silently blocked).

- **🎬 Tablet video playback (offline snippets)** — the tablet's **page 2 ("Video Snippets")** plays **pre-downloaded** YouTube clips **fullscreen in IINA on the Retina**, seeking to a per-video start second, instead of opening the live URL in Chrome (the old `/open` path). Videos live in the **gitignored `videos/`** folder (`<youtubeId>.mp4` + a `videos.json` manifest of `{id,title,startSeconds,file,url}`), downloaded/registered by the **`add-training-video` skill** (`.claude/skills/add-training-video/` — `yt-dlp` forced to **H.264/AAC MP4** so AVFoundation can play it; `brew install yt-dlp`, ffmpeg already present). `VideoLibrary` reads the manifest and serves `GET /videos`; the tablet fetches that and builds tiles **dynamically**, so **adding a video needs no APK rebuild** (the page only re-renders when the list changes — no ▶-placeholder flashing on reopen). **Every entry carries its tile image inline**, so the tablet needs no network of its own beyond this one call: `VideoLibrary.thumb(for:)` returns the manifest's hand-written `thumb` when there is one and otherwise pulls a frame out of the downloaded mp4 with `AVAssetImageGenerator` at the snippet's **own start second** (never 0 — a clip that fades in from black would cache a black tile), scaled to 480 px and cached beside it as `videos/<id>.jpg`, which doubles as the override: drop your own JPEG in and it is served verbatim. `warmThumbnails()` renders the missing ones in the background at startup, because an exact seek into a 90 MB mp4 costs the best part of a second and thirteen of them *inside* the request would time the tablet out. This replaced a tablet-side fetch of `img.youtube.com/vi/<id>` (`maxresdefault` → `mqdefault`, **3 s connect + 5 s read per URL per video**) which is what left page 2 on ▶ placeholders on a filtered venue hotspot — and which made the list and its images two sources of truth that could drift. Tablet-side the answer is also **persisted**: the parsed `/videos` body is written to `filesDir/videos-cache.json` and read back in `onCreate` *before* the page is built, so a cold start (the app auto-starts on boot) paints the real tiles with zero network. The snapshot is never authoritative — it is exactly what the Mac last said, overwritten wholesale by the next live fetch. Tapping a tile hits `GET /video/play/<id>` (optional `?t=` start override → the tablet sends one request via `MacLink.getSyncFast`); `VideoPlayer` **orchestrates the external IINA player** (not an in-app AVPlayer): it launches `iina-cli --no-stdin --mpv-start=<sec>`, a new play **replaces** the previous player (`pkill -x IINA` before relaunch, so windows never stack), and the player is **auto-killed ~60 s after start** so a snippet never lingers on the projector. Three things IINA does *not* do correctly on its own, each fixed here after being watched misbehave: **(1) which screen** — the clip must land on the **built-in Retina whatever macOS calls the main display**, because the Retina is what a venue projector mirrors while at a venue the *ASUS* is made primary (`DisplayArrangementManager`), so "main screen" is exactly the wrong answer there. mpv's `--fs-screen` is **ignored** (verified: IINA manages its own `NSWindow`), so the window is launched *windowed*, moved onto the Retina through the **Accessibility API** (same in-process grant as `TerminalTiler`, no Automation consent) and only then fullscreened via `AXFullScreen` — in that order, because a fullscreen window can no longer be moved between displays. Two traps: IINA exposes **several AX windows and the first is not the player** (a 1728×37 `AXUnknown` strip whose `AXFullScreen` isn't even settable — writing frame + fullscreen there silently did nothing while looking like success), so `playerWindow(among:)` picks the largest **`AXStandardWindow`**; and the fullscreen request is **repeated until the attribute reads back true**, since IINA puts a window up before it can be fullscreened and an early write is accepted and ignored. The Cocoa→AX coordinate flip (y **up** from the primary's bottom vs **down** from its top — identical only for the primary screen, i.e. everywhere except the venue layout) is pure and unit-tested in `VideoPlayer.axFrame(screenFrame:primaryTopY:)`. **(2) nothing plays next, ever** — IINA loads the *containing folder* as a playlist, so a finished snippet rolled straight into the next file in `videos/` on the projector (observed: "Papaguera" → "Feel it coming"); neither `playlistAutoPlayNext=0` nor `--mpv-autocreate-playlist=no` stopped it, so the clip is played from a **staging folder holding exactly one file** (`videos/.play/`, a **hardlink** — not a symlink, precisely so resolving it can't lead back to the folder full of siblings — rebuilt per play). Verified by `playlist-count: 1`. **(3) the end of a clip rewinds and pauses** — with `--mpv-keep-open=yes` mpv freezes on the last frame, which leaves a still on the projector and needs a seek before it can be replayed, so the player is watched over **mpv's JSON IPC socket** (`--mpv-input-ipc-server`, `MpvIPC`: one connection per command, every failure = nil) and told to seek back to the snippet's start second and pause the moment it reports `eof-reached` — leaving it primed so **SPACE replays the clip**. Resuming re-arms both the watch and the auto-kill, so a replay gets a full 60 s of its own instead of being cut off by the first play's deadline. `GET /video/stop` closes it. Headless hooks: `GET /test/video/<id>` (play at the manifest second) and `GET /test/video/stop`. **Local clips (no YouTube id) are supported too** — a manifest entry may carry a `thumb` (base64 JPEG, extracted with `ffmpeg` and served inside `GET /videos`) instead of relying on `img.youtube.com/vi/<id>`, with a made-up id as its key (`fearLocalClip`, `papaguera`). Those are added by hand (copy the mp4 into `videos/`, grab a frame, upsert the entry); the `add-training-video` skill only covers YouTube URLs. **Subtitles are sidecars, passed explicitly** (`sidecarSubtitle(for:)`): a `<id>.srt` (or `.ass`/`.ssa`/`.vtt`/`.sub`) next to the mp4 is hardlinked into `videos/.play/` along with the clip and handed to the player as `--mpv-sub-file=<path> --mpv-sub-visibility=yes`. Two reasons it is not left to mpv's own `sub-auto`: the clip plays from the **staging folder**, so a sidecar that stayed behind in `videos/` would never be looked at, and a `sub-visibility=no` sitting in a personal `mpv.conf` would swallow it without a word. A sidecar rather than a muxed track because the mp4s are **downloaded artefacts** — re-fetching a clip must not throw its subtitles away. Failing to link the sidecar does *not* fail the staging: the clip still plays alone (subtitle-less beats auto-advancing into the rest of the library). Currently only **Sinking** (`KLSdOY-6R_U`, the Berlitz German coast-guard ad) carries one — the joke is a mispronunciation, so the room reads it faster than it hears it, and the punchline word is italicised in the cue. The `.srt` is **gitignored along with `videos/`**, so it is local runtime data like the mp4s: regenerate it with `mlx_whisper` over the extracted audio if the folder is ever rebuilt. **Strip any baked-in letterbox before adding a clip** (`ffmpeg -vf cropdetect` to find it, then `crop=`): black bars inside the file are not black bars the player can remove, and they stack with the aspect-ratio bars on screen — Papaguera arrived as 640×480 with only 640×344 of picture, i.e. 28% of the frame was baked-in black.
- **🔌→🤖 Tablet app auto-deploy, on USB or WiFi (`AndroidAppDeployer` + `AndroidDeployPolicy` + `WirelessTabletLink`)** — plugging the tablet into the Mac rebuilds and reinstalls the **LaunchBreak Android app** when the tablet is carrying an older build. The tablet is deployed to by hand between workshops, so it drifts behind the Mac add-on it talks to (new sounds, new tiles, a changed protocol) and nothing says so until something misbehaves in front of a room; the cable going in is the one moment the Mac can fix that itself. The trigger is `UsbTunnelKeeper.onTunnelArmed` — the **armed** edge, not the raw IOKit attach, so adb is already answering (the two share one `UsbTunnelKeeper.adbPath`, hence one adb server). **"Behind" is a source stamp, not a version:** `versionName` never changes and a rebuilt APK hashes differently every time (zip timestamps), so the Mac stamps the *sources* — the HEAD commit when the tree is clean, plus the newest edit's timestamp when it is dirty (so every uncommitted save deploys on the next plug, while ten plugs after a no-op pull deploy nothing) — and, **only after a successful install**, `adb push`es that stamp to a marker on the tablet (`/sdcard/victor-launchbreak-deploy.stamp`, on `/sdcard` rather than in the app's data dir so it survives the reinstall it describes). A **missing** marker deploys once, deliberately: what's on the tablet is then unknown, and assuming it's current is the expensive mistake. The gradle build runs **only after** the stamp says so, so the common case (cable in to charge, sources unchanged) costs one `adb shell cat` — no build, no reinstall, no app restart, no notification. On a deploy: `./gradlew assembleDebug` → `adb install -r` → best-effort `pm grant WRITE_SECURE_SETTINGS` + `settings put global audio_safe_volume_state 0` (keeps Android's headphone-safety dialog off the soundboard) → **force-stop + relaunch** (`install -r` leaves the old process running the old code) → write the marker. **`JAVA_HOME` is resolved, never assumed** — a LaunchAgent-started app inherits almost nothing, and AGP 8.7 runs on JDK 17–21 while this Mac also has 22–25 installed, so the candidates are `VICTOR_ANDROID_JAVA_HOME`, sdkman's `current` (what Victor's own shell builds with), then `java_home -v 21/17`. Both outcomes raise a **native macOS notification** (`AppDelegate.postAndroidDeployNotification`): `Android app updated to version` / `4 Aug 2026, 19:41 · a1b2c3d`, or `Android app update FAILED` naming the step — a deploy that failed silently is worse than one that never ran, since the tablet then keeps the old build while Victor believes it's current. A stamp that just failed is not retried for 10 min (a broken build fails the same way every time), and an `inFlight` flag collapses replug bursts. **A freshly plugged cable is given 8 s to settle before the deploy starts, and `adb install` gets 3 attempts 4 s apart** — the very first deploy this ever ran began 3 s after the armed edge and its install died mid-transfer while the USB tunnel re-armed underneath it, which is precisely the manual replug this feature exists to remove. The command runner also **joins its output reader** instead of sleeping "long enough": the truncated tail is exactly where the reason a command failed is written (that install reported only `failed to install …:`, cause cut off). **It deploys to the tablet, and only the tablet.** It used to address "the adb device", singular — a notion adb does not have; with one device attached it simply uses it. So the morning Victor plugged his **phone** in, the tablet's LaunchBreak APK was built and installed onto the phone, granted permissions there, force-stopped and relaunched there, and the marker was written to the phone's `/sdcard` — every log line reading like a clean deploy. Now every `adb` call carries an explicit `-s <serial>`, and the serial comes from `AndroidDeployPolicy.pickTablet`: a **positive** test (`ro.build.characteristics` contains `tablet`, or the model matches `tabletModels`) because the cost of guessing wrong in the other direction is installing on a device Victor did not mean to touch, silently. Two candidates **refuse** rather than pick — `VICTOR_TABLET_SERIAL` breaks the tie. A non-tablet on the cable is a normal, silent skip (the phone charges there all day; a notification each time would be noise), and only a *forced* deploy reports why nothing happened. `UsbTunnelKeeper` is gated the same way — a bare `adb reverse` to the phone would have reported the tunnel armed and handed the phone straight back to the deployer. `GET /test/android-deploy` now lists every attached `devices[]` with its model and characteristics plus the resolved `tablet_serial` / `tablet_error`, which is the fastest way to check the tablet is still recognised. Decision + wording are pure and unit-tested in `AndroidDeployPolicy`. **Accepted caveat:** a deploy **restarts the tablet app**, so a mid-workshop replug *with moved sources* blinks the LaunchBreak UI — gating that on "not during a session" would mean the deploy never happens on the day it matters. Test hook: `GET /test/android-deploy`.
- **📶→🤖 …and the same deploy over WiFi (`WirelessTabletLink`)** — the cable is an IOKit event the Mac cannot miss; WiFi is something you have to go and look for, so this is a **poll** (60 s on AC, 300 s on battery) rather than another hook. The tablet's wireless debugging is paired, so adb can reach it with no cable at all — but only after someone runs `adb connect`, and nobody was running it, so the tablet would sit on a three-commit-old APK all morning looking current until the first tile press did the wrong thing. Each tick asks `AndroidDeployPolicy` whether a tablet is reachable on *any* transport; if one is, it fires the same `tabletConnected()` edge the cable does (edge-triggered, so a tablet on the network all day deploys once, not every minute) and the stamp check makes a redundant tick cost one `adb shell cat`. If none is, it discovers one: `adb mdns services` → `adb connect <ip:port>` → re-ask the picker over the link that just came up → `adb reverse tcp:55123 tcp:55123`. **Which device it connects to is the whole safety question**, and it is answered by never connecting to one it cannot already name: the mDNS service name embeds the hardware serial (`adb-HVA5HP4L-b2mjKy  _adb-tls-connect._tcp  192.168.101.66:40633`), and only the serial learned from a previous sighting (persisted in `UserDefaults`, normally taught by the cable) is matched — before that first sighting it does nothing at all, rather than risk `adb connect`ing to the phone, which is the exact failure `pickTablet` exists to prevent. The **reverse tunnel is armed over the wireless transport too**, which is the non-obvious half: the tablet keeps winning on `localhost:55123` instead of falling back to its LAN/mDNS/relay chain, so routed sound behaves identically with no cable in. `adb connect` **exits 0 even when it fails**, so its output text is the verdict, not its status. **The TLS port is not stable** — wireless debugging picks a new one on every toggle and reboot — which is why the endpoint is rediscovered through mDNS each time instead of remembered alongside the serial. Measured end to end: 41 s from `adb disconnect` to reconnected + tunnel armed, then a full gradle build → `adb install -r` over WiFi → marker written.
- **One tablet, several doors.** Turning wireless debugging on makes a single tablet list itself two or three times over — `HVA5HP4L` (cable), `192.168.101.66:40633` and `adb-HVA5HP4L-…._adb-tls-connect._tcp` — and `pickTablet`'s ambiguity guard, written for "the phone is also on the cable", read that as several tablets and **refused to deploy at all**, silently (the passive path never notifies). So `Device` now carries `ro.serialno`, the *hardware* identity, and candidates are collapsed by it before they are counted: several doors into one tablet is one tablet, two genuinely different tablets still refuse. When both a cable and a wireless transport are open the **cable wins** — faster for a 25 MB APK, and the venue's access point cannot drop it mid-install. Both getprops (`ro.build.characteristics`, `ro.serialno`) go over in one `adb shell`, since this runs per device on every poll.
- **🌙→🤖 A locked Mac puts the tablet into standby (`ScreenLockMonitor`)** — while the Mac's screen is locked, the tablet dims its backlight to 5%, lays a 70%-black scrim over the UI (a scrim rather than a view alpha: fading the tree only blends it toward the light background behind the grid, which came out washed-out pale grey — still lighting the room, which is the one thing this mode exists to stop), blacks the action bar and draws the video page as bare stroked outlines (a hollow ▶ low in each tile) instead of thumbnails. The problem is the hotel room, not the workshop: a laptop left on overnight locks itself, and the soundboard beside it used to burn at full brightness till morning. The lock is the one signal meaning *nobody is looking at either screen*. **A Mac that merely stopped answering is not that signal** — the link drops for network reasons (a filtered venue hotspot, a Wi-Fi handover) while both devices are in heavy use, so the tablet clears the flag on disconnect rather than latching the last "locked" it heard; blanking the board mid-session is the failure this avoids. macOS publishes the state as two *distributed* notifications (`com.apple.screenIsLocked` / `…Unlocked`) — the only non-deprecated cross-process way to hear it — and since those are edges, the current state is seeded at startup from `CGSessionCopyCurrentDictionary()["CGSSessionScreenIsLocked"]` (the app is LaunchAgent-started and can be restarted while the screen is already locked). It rides to the tablet as `macScreenLocked` on the existing `/ping`; every decision about *how* to look asleep is the tablet's. **Waking is a touch, and the touch is swallowed** — the finger lands on a screen too dark to read, so letting it through would fire whatever tile was underneath; the whole gesture (not just the DOWN — a bare UP still lands on a button) is consumed. A touch buys 60 s, re-armed by every further touch, which covers both cases: a break spent pressing tiles never dims mid-press, while one accidental brush at night lights the tablet for a minute and it puts itself back to sleep. Unlocking the Mac ends standby immediately. **Lid-close and shutdown are deliberately not mirrored** — Victor closes the laptop to travel and shuts the tablet down at the same time, so there is nothing there to solve. Test hooks: `GET /test/screen-lock`, `GET /test/screen-lock/simulate/<1|0>`.
- **📱→🤖 Phone low battery mirrored to the tablet (`PhoneBatteryMonitor` + `PhoneBatteryPolicy`)** — when Victor's **phone** (not the Mac, not the tablet) is nearly flat, the tablet pulses a bright red chip — black phone glyph, black percentage — in the top-left of its action bar, above the tiles, until the phone is back on a charger. macOS *already* warns about this — Soduto, the KDE Connect client, posts a "Low Battery | <phone>" notification — and that notification is precisely the one that gets missed: it lands on the screen being projected to the room, or behind a fullscreen deck, while nobody is looking at the Mac. The tablet is in eye-line all day, so the warning is doubled there. **The notification IS the state machine, which is why it is the source and a percentage isn't.** Soduto keeps the peer's battery status purely in memory (`BatteryService` builds no menu item, writes no preference, exposes no API — nothing outside the process can read it), but what it *does* publish behaves exactly the way Victor asked: it posts the notification on the phone's low-battery threshold event, **re-delivers it with the fresh percentage on every subsequent battery packet while the phone stays low, and removes it the moment the phone reports charging**. So presence of the notification is the warning and "until you plug it in" comes for free — we never track charging ourselves. Mechanically the Mac reads macOS's own notification store (`~/Library/Group Containers/group.com.apple.usernoted/db2/db`) every 30 s, matching `app.identifier = com.soduto.soduto` (lowercased there, unlike the bundle id) **and** an `NSUserNotification.identifier` starting with `com.soduto.services.battery` — the identifier, not the localized title, is what separates a battery notification from Soduto's pairing / share / SMS ones. The store is **WAL-mode SQLite and is copied aside before it is read** (`db` + `db-wal` + `db-shm` → a temp folder, queried, deleted): a read-only connection to a WAL database still needs to write the `-shm` index, and skipping the `-wal` would be cheaper and wrong — the newest notifications are exactly the ones still sitting in it. The reading rides to the tablet on the existing `/ping` (`phoneBatteryLow` + `phoneBatteryPct`); the blinking itself lives entirely on the tablet. **Three guards.** Only a charge **under 30%** warns at all (`PhoneBatteryPolicy.warnBelowPct`): Soduto has been caught re-delivering its battery notification carrying a *full* battery, which left the tablet blinking all day at nothing, and a warning that cries wolf stops being read — so the percentage in the body overrules the notification's mere presence. The tablet applies the same floor itself (`MainActivity.WARN_BELOW_PCT`), so an old build of either half is harmless alone. A notification nobody has refreshed for **90 min** stops warning (`PhoneBatteryPolicy.staleAfter`) — a phone that goes flat and switches off never sends the charging packet that would clear it, and would otherwise blink the tablet forever; while the phone is genuinely connected and low it drains fast enough that packets keep arriving well inside that window. And the tablet clears the mark whenever the Mac link drops, since it is the Mac that decides when the warning is over. **Requires Full Disk Access** — the only thing in this app that does, and it is not granted by default; the first denied poll raises a native notification saying so, because a feature that silently never fires is indistinguishable from a phone that never runs low. Decisions are pure + unit-tested in `PhoneBatteryPolicy`, and `PhoneBatteryMonitorTests` runs the real query against a fabricated store built with usernoted's schema. Test hooks: `GET /test/phone-battery`, `GET /test/phone-battery/simulate/<pct>` (simulate a value under 30 — anything above the floor correctly shows nothing).
