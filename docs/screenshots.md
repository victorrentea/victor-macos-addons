# Screenshots (⌃P)

- **📸 Screenshot (⌃P) — clipboard AND disk, always both** — captures the display under the cursor, puts it on the pasteboard (PNG + TIFF, so both the clip-stack poller and a CLI can read it) **and** files it as `~/Library/Caches/ro.victorrentea.macos-addons/screenshots/YYYY-MM-DD_HH-mm-ss.jpg`. There used to be two shortcuts — ⌃P to the clipboard, ⌃⇧P to the session folder — and choosing between them is a decision nobody makes correctly mid-workshop: you take the shot to paste it somewhere, and only hours later, writing the summary, discover it was worth keeping. So **⌃⇧P is gone** (VS Code gets its Command Palette back; the tap's branch now requires `!hasShift`) and there is one menu item. **The border flash is raised the instant `screencapture` exits — before the clipboard work, not after it**: re-encoding a retina capture to PNG *and* TIFF costs hundreds of milliseconds, and doing that first pushed the yellow border that far behind the keypress, which simply read as "⌃P is laggy". It cannot be raised any earlier than the capture: the flash is a real window, so anything drawn before the shot is drawn *into* the shot. **Held, ⌃P becomes the crosshair crop** (`screencapture -i`) — the tool ⌃⇧P used to reach, minus the decision: you no longer pick "full or crop" before pressing, you pick it by how long you keep the key down. **Nothing fires on the keyDown**: which of the two you meant is answered on the *release* — under `ScreenshotHoldPolicy.holdSeconds` = 0.45 s takes the screen, over it opens the crosshair (an **autorepeat** keyDown answers it earlier, so with key repeat on the crosshair appears while the key is still down; the keyUp is the fallback where repeat is off, and is the only reason `keyUp` is in the tap's event mask). The first version instead fired the full-screen shot on the keyDown, to keep a tap free of any "is this a hold?" delay — but that delay is not what waiting costs: the release costs only the length of the keypress itself (~100 ms for a tap), while firing early meant every hold took a full screen nobody asked for **and flashed a whole-screen yellow border over the crosshair already waiting for the drag**. So no shot, no border, and nothing to clean up afterwards. Esc cancels the selection, which writes no file, and nothing else runs: the clipboard and the folder are left exactly as they were. **The border a crop gets is drawn around the crop**, not around the screen (`ScreenCaptureFlash.flash(around:)`, a ring sitting entirely **inside** the region, fading inward from its edges exactly the way the screen-sized flash fades in from the screen's — so what lights up is the captured pixels themselves; drawn outside it read as a frame *around* something, which is the wrong answer to "what did I just take"): a whole-screen frame after a selection claims the wrong thing, since not taking the whole screen is what the crop was for. `screencapture` reports nothing about the region it took — the jpg carries a size and no origin — so the rectangle is reconstructed from the drag that made it (`CropDragTracker`: the cursor position when the left button went down and came back up, sampled every 8 ms off `CGEventSource.buttonState`, which is session *state* and so cannot be starved by screencapture's overlay swallowing the mouse the way an event tap would). It is then **checked against the saved file's own pixel dimensions** (`CropFlashGeometry.matchesCapture`, pure + unit-tested, with the CG→Cocoa y-flip): a space-bar window pick is a click, not a drag, and anything that doesn't line up draws **nothing at all** — a border in the wrong place is worse than no border. Two traps found by driving the whole thing with synthesized drags, both of which outlived the keyDown-capture design: two captures can be **named in the same second** and the second then overwrote the first, so every capture goes through `ScreenshotManager.uniqueURL`, which appends `-2` after the timestamp the summarizer skills parse; and a border of ours raised over the crosshair puts a window above screencapture's own selection overlay — observed to end with the selection cancelled and no file written — so a crop **suppresses** screen-sized flashes for its whole duration (`beginSuppression`/`endSuppression`) rather than only cancelling the ones already on screen. The menu carries **one** item, **📸 Screenshot (hold to crop)**: clicking it takes the whole screen (a click cannot be held) and the title is where the other half of the shortcut is taught, since a hold is the one gesture nothing on screen reveals. A second row for the crop would have been one you can never usefully click, explaining a key you already have. The file is the capture and the clipboard is a **copy of that file**, not a second `screencapture -c` run: two runs are two different moments, and the picture you pasted has to be the picture the summary can quote. **Caches, not `/tmp`, because these files must be reclaimable**: Caches is the one folder emptying the Trash, Storage Management and every cleaner tool actually reach, and macOS may purge it under disk pressure — all welcome, because the folder is a staging area, never an archive. It also bounds itself (`ScreenshotRetentionPolicy`, pure + unit-tested, pruned off the capture path after every shot): older than **14 days** or past a **2 GB** total and the oldest go, except the **newest file, which is never deleted** — that is the guard against a wrong clock throwing away the capture taken one second ago, the one about to be pasted. **The cursor's position rides in the filename** — `2026-08-14_00-34-42_at1200x500.jpg`, global CG points (y down from the primary's top, so a screen to its left gives negatives), sampled *before* the shutter since that is what `-C` draws into the picture. The shot shows the pointer but nothing in it says which display coordinate that was, and a summary reading the folder months later cannot recover it. The same point is marked **on screen** for ~2 s by the minigun's red aiming reticle at half its aiming size (`ScreenCaptureFlash.markCursor` → `EmojiAnimator.makeSniperReticle`), at **80 % opacity from the first frame** with the only fade in its last quarter: a mark that fades *in* asks to be watched arriving, and this one is already there when you look. It **zooms out** as it lands — in at 1.3×, settling to 0.9× over 0.35 s — so it reads as a scope being brought down onto the spot, and what stays behind is the smaller, quieter mark rather than the loud one that arrived. The border says what was captured; this says where you were pointing while the transcript recorded what you were saying about it. NB the anchored filename regex in the training-summarizer's `screenshot_index.py` had to learn about trailing detail (`_at…`, and the `-2` uniqueness suffix) — anchored on `\.jpg$` it silently dropped exactly those files. The timestamped name is what lets the `training-summarizer` / `call-summary` skills line each shot up against the transcript's `[HH:MM]` stamps and rank them by **dwell** (minutes until the next shot × words actually spoken over it, `screenshot_index.py` in the training-summarizer skill); anything a summary keeps is **copied into the session folder** by the skill that keeps it, so a cache wipe can never break a published note. `ScreenshotManager.sessionFolder` survives for `SessionNotesAppender` only — screenshots no longer go there
