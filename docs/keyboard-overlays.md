# Keyboard / Emoji Cheat-Sheet Overlays (⌥, ⌥⇧, ⌘⌃)

- **⌨️ Hold-to-see cheat-sheets (`KeymapOverlay`)** — holding a modifier long enough to be *asking* rather than *typing* draws a keyboard on the secondary screen. Four sheets, one renderer, one hold delay (`KeymapHoldCoordinator.delay`: 0.3 s multi-monitor, 1.0 s single, since on one screen the sheet covers what you're doing): **⌥ / ⌥⇧ / ⌃⌥** show the emoji/character each key emits, read from `EmojiKeyLayer` — the same map the event tap types from, not the `.keylayout`, which stopped being the source of those characters when the app took the rewrite over; **⌘⌃** shows what this app's own ⌘⌃ shortcuts *do*, one word per key (`terminal`, `claude` on C (**Q says `salut` with a 👋 accent**: it said `claude` too while ⌘⌃Q opened a permissions-bypassed terminal, and two identical words on one board is a key you press wrong at speed. It left the sheet on 2026-09-09, when the 🤖 mascot moved to ⌃⌥G and the combination went back to macOS's Lock Screen, and came back with it on 2026-09-10 — ⌃⌥ became the third emoji board and G was needed for the goose, so the wave returned to the key it was written for and shadows Lock Screen again), `notes`, `wispr🎙️`, `tile`, `SRL`, `zoom`, `email`, `catalog`, `todo`, `relay` on D with a 🎯 accent). Three keys answer with a **picture instead of a word**, because a mark is recognised faster than the name of the thing: **L = 📅** (calendar), **G = the Gmail logo** and **N = the Google Docs logo** (the "notes" doc itself — the mark *is* the destination, where S's `notes` is the act of sending something there). The two emoji stay in `CommandControlShortcuts.labels` and are detected by the pure `KeymapOverlayRenderer.isPictogram` — a label that is *nothing but* emoji is drawn big and centred in the whole payload area instead of being shrunk to word size at the bottom (`wispr🎙️` is a word that merely *contains* one, so it must not qualify). The Gmail and Docs marks are bundled PNGs (`Resources/gmail-logo.png`, `Resources/gdocs-logo.png`, listed in `CommandControlShortcuts.artworkNames`, loaded through `artworkImages()`) drawn **straight onto the key with its own transparency intact — no white plate behind it**: every key on this sheet is one flat black, so a white card under a single one is the loudest thing on the whole keyboard. The mark survives the dark background because the M *is* the coloured part; the envelope body Gmail normally paints white simply reads as key. A key carrying artwork counts as **bound** even though its `labels` entry is absent, so `boundKeyCodes` (labels ∪ artwork) — not `labels.keys` — is what the sync test asserts. Four keys also carry a small **corner accent** (`CommandControlShortcuts.accents`) in the top-right, opposite the base letter: **E = @**, **Z = 🔗**, **S = 🚀**, **R = 📋**, **K = 📕** and **M = ✉️**. Their words ("email", "zoom", "notes", "SRL", "catalog", "todo") are nouns — the *thing*, not what happens to it — so the mark supplies the missing verb a beat faster: 🚀 says the selection is launched into the notes, 📋 that the SRL details are pasted rather than opened, 📕 which book "catalog" means; it is drawn at 28pt against the letter's 42 precisely so it reads as a hint on the key and not as a second key label. A test asserts every accented key is one that's actually bound — an accent on a dimmed key would decorate nothing. Which sheet a combination asks for is the pure, unit-tested `KeymapHoldCoordinator.sheet` — deliberately exact, so anything with ⌘ on top of ⌥ (⌘⌃⌥D dark mode, ⌘⌥ generally) shows nothing rather than guessing. **⌃⌥ was in that list until 2026-09-10** and now has a sheet of its own; it is still a shortcut prefix too (⌃⌥V, the notes paste), and those keys are simply the ones the sheet has nothing to say about. The word sheet renders through the same `KeymapOverlayRenderer` in `.word` style: the letter shrinks to the top-left corner to make room, the word wraps across the bottom at a size chosen by its length (`wordFontSize` — word-wrap cannot break a single word, so an oversized font spills over the key border instead of wrapping), and **keys with nothing bound are dimmed to 22% while bound ones keep the full-brightness border**, so the eye lands only on what's live. The ⌘⌃ image is built **in the controller's `init`, not from the layout file**: those are app shortcuts, not characters, so a failure to locate the `.keylayout` must not take the shortcut sheet down with it (which also means `images` is never empty — the layout retry now asks `images[.option] == nil`). Pressing any key under either modifier drops the overlay (`keyDownWhileModifierHeld`): the hold turned out to be a real shortcut. `CommandControlShortcuts.labels` is the map and **must stay in sync with the ⌘⌃ branches in `EventTapManager`**; a test asserts the exact key-code set. Two deliberate exceptions to that rule, both documented in the map: **⌘⌃W is on the sheet but NOT bound here** — it is Wispr Flow's "paste transcript", and the sheet answers "what does this combination do on this Mac", so an empty key would be the wrong answer. Since 2026-09 **neither ⌃W nor ⌘⌃W is bound in this app at all**: ⌃W belongs to `victor-effects` (the 🔥 whip), ⌘⌃W is Wispr Flow's, and the two coexist only because the effects tap's whip rule requires `!hasCmd`. The sheet's answer is unchanged — the key does something on this Mac, just not in this process; (**⌘⌃V used to be the second exception**, bound but deliberately blank, because while it meant the emotional paste it would have put a second "paste" on a board where ⌘⌃W already says it — and two keys reading the same word makes the reader pick wrong at speed. It now reads `spus` with a 🎙️ accent: what the key does is no longer a paste at all, and "said" is the one word that separates text coming out of your mouth from text coming off a clipboard.) The **Emoji Overlay** menu item toggles all of them.
- **The ⌥ sheet is a palette, the ⌘⌃ sheet is a menu (`KeymapHoldCoordinator.keyDownWhileModifierHeld`, 2026-09-09)** — pressing a key while the modifiers were still held used to take *any* sheet down, on the theory that the hold had turned out to be a real shortcut rather than a question. That is right for ⌘⌃: the key just pressed **is** the choice, the shortcut has fired, and what stays on screen is a picture of a menu nobody is reading any more. It is exactly wrong for ⌥ / ⌥⇧, which is the case the sheet exists for — ⌥ is still down *because the next emoji is coming*, and hiding the layout after the first character hides it from the one person using it, someone picking a row of characters off a layout nobody has memorised. So only `.commandControl` tears down on a keypress now; the ⌥ layers stay up until ⌥ itself is released (`reset()`), and swapping ⇧ in and out mid-hold still switches between the two of them.
- **The ⌃⌥ board (2026-09-10)** — a third emoji layer, sitting beside ⌥ and ⌥⇧ in the same `EmojiKeyLayer` map file (`~/.victor-emoji-layer.json`, section `controlOption`) and drawn by the same renderer in `.glyph` style. It exists because **the ⌥ layer ran out of letters years ago**: 🪿 is on ⌥8 because G was long gone, and a digit is something you look up where a letter is something you remember. ⌃⌥ is also the least-colliding pair left on this Mac — macOS binds almost nothing to it, apps rarely do, where ⌥⌘ is the busiest combination there is. It opened with one key, **⌃⌥G = 🪿**, and ⌥8's goose stays exactly where it was: the new board adds a letter that means the word, it does not move a digit that already works. It grew two more the same afternoon — **⌃⌥B = 🐛** and **⌃⌥P = 🪂** — and the parachute is the case where a digit *did* move: it was on **⌥⇧8** and is now only here. The two are not a contradiction. ⌥8 is years of muscle memory and breaking it would cost more than the letter is worth; ⌥⇧8 was a digit on the shifted board that nobody had ever learned, so moving it broke nothing — and leaving 🪂 on both keys would only mean one of them gets typed by accident. The rule the board is settling into: a letter that means the word wins, unless the digit is already a habit. A seed change alone does **not** reach the running Mac — `~/.victor-emoji-layer.json` already exists, so the seed is only what a fresh machine starts from; both were edited, which is why the keys work without a rebuild. **No ⇧ variant, on purpose** (`EmojiKeyLayer.Layer`): ⌥ needed one because ⌥⇧ arrived as a full layout's worth of characters inherited from `Victor-v27`, while this board starts at one key — so ⌃⌥⇧G types the goose too, and asks for the same sheet, rather than reaching a second, empty one. A `.keylayout` could never have carried any of this: macOS derives control characters itself rather than asking the layout (which is why `Victor-v27`'s own ⌃ emoji sat inert for years), so the board only exists because the tap owns the rewrite — and for the same reason the rewrite must strip **⌃ as well as ⌥/⇧** off the event, or the character arrives as a chord and the app derives a control code from it instead of inserting it. The branch sits **above every ⌃⌥ shortcut in the tap**: a letter the map claims is an emoji key and nothing else, and one it doesn't claim falls straight through, so ⌃⌥V still appends the clipboard to the notes. Adding a key is one line in the JSON and takes effect on the next keystroke — the sheet redraws itself off `EmojiKeyLayer.generation`. A map file written before this layer existed has its `controlOption` section **backfilled from the seed on load**, keeping every other section byte-for-byte: rewriting the file from the seeds instead would silently revert every emoji Victor has changed since.
