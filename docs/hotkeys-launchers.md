# Hotkeys & Launchers (EventTapManager)

Global ⌘⌃* shortcuts that open terminals, apps, docs and paste snippets, plus the clipboard/scroll niceties riding the same event tap. The hold-to-see cheat-sheets that document these keys live in `keyboard-overlays.md`; the ⌘⌃S notes shortcut lives in `session-notes.md`; ⌃P lives in `screenshots.md`.

- **🤖 Claude (⌘⌃C) / Claude with permissions bypassed (⌘⌃Q) / plain Terminal (⌘⌃T)** — all three open a Terminal in `~/workspace`, **in the quarter of the screen the cursor is in** (`MenuBarManager.screen(containing:)` + `quarter(of:on:)`): the shortcut is reached for while looking at one spot, so that spot is the answer to "where do you want this". The screen half of that rule came first — pinning the window to the built-in Retina, as this originally did, puts it on the projector mid-workshop — and the quarter followed for the same reason one scale down: `.bottomLeft` was hardcoded, so reaching for a terminal while reading the bottom-left of a screen dropped it on exactly what you were reading. **Both come from ONE `NSEvent.mouseLocation` sample**, taken in `openWorkspaceTerminal` and passed to both helpers: two separate reads can straddle a screen or quadrant edge while the hand is still moving, and the window would then be sized for one screen and placed by the geometry of another. NB the cursor is sampled when the hotkey's async block runs, a few ms after the key went down — not at the tap itself. ⌘⌃Q runs `claude --dangerously-skip-permissions`. **The command is typed into the window by `do script` (2026-08-14), which reverses the script-file design — one process is worth more than the race it closed.** For a while the command travelled in a `/tmp/victor_claude*.sh` file passed as the shell's argv, because `do script "claude"` writes its characters into a tty whose window already has keyboard focus, so a prompt Victor starts typing in that gap interleaves and the shell runs `clahelloude`; the script also drained the tty (`stty -echo` + `while read -t 0 -k 1`) so early keystrokes couldn't land in claude's startup either. What that cost was invisible until the process tree was actually read: **Terminal runs an opened document from the window's own login shell**, so every claude window carried a permanent extra zsh — `login → zsh --login → zsh -l victor_claude.sh → claude` — for a race that needs a keystroke inside the ~200 ms the window takes to appear and announces itself immediately when it happens. Typed again, the tree is `login → zsh --login → claude`. Two consequences follow from the shell being **interactive** again: `~/.zshrc` loads, so the window cds itself to `~/workspace` (no explicit `cd` to print) and aliases exist — ⌘⌃Q still spells the flag out rather than using `cx`, purely so renaming the alias can't break the hotkey. `do script` is also **synchronous with the window's creation**, so `set bounds` follows on the next line and the old `open -a Terminal` + window-count polling loop (which existed because `open` is async and would otherwise resize the *previous* window) is gone with it. The two per-repo launchers in the Extra submenu (`openDreamClaude`) were converted the same day for the same reason. ⌘⌃T opens an empty window (`do script ""`) — there is no command to garble. NB the remaining shells in a claude window are not ours: `login -pf` is Terminal's own, and claude itself spawns a zsh snapshot at startup plus one per Bash tool call. A `zsh (kiro-cli-term)` layer used to sit in there too, from Kiro CLI's shell integration; it was uninstalled (`kiro-cli integrations uninstall dotfiles`) the same day. **Each of the three then tiles that screen** (`TerminalTiler.tile(onDisplay:)`, 0.6 s after the AppleScript returns so Terminal's own `set bounds` has settled): a window already sitting in the quarter the new one just claimed would simply be covered — the whole point of opening a second terminal is to see both. Only the display the window landed on is touched; terminals on the other screens keep their frames, because the shortcut said "make room here", not "rearrange all my monitors". NB ⌘⌃Q **shadows macOS's own ⌃⌘Q "Lock Screen"**: the `.cgSessionEventTap` sees the key first and swallows it, so the Mac no longer locks on that combination.

- **🎧 Focus playlist (⌘⌃F, `FocusPlaylist`)** — opens Victor's YouTube focus mix (`RDLEEx_UkHmBU`) in Chrome's front-window profile, **on a random track**, as a tab on the screen the mouse is on (`openUrlInChromeOnMouseScreen`, so it never lands on the projected Retina). F is for *focus*: the word names what the music is for, not the site it comes from — "youtube" would have described three other keys equally well. **The random start has to be built by hand, because YouTube offers no lever for it**: on an `RD…` radio list `&index=` is ignored (`watch?list=RD…&index=12` and `index=1` both resolve to the same video — measured, not assumed), `&shuffle=1` is ignored outright, and a `v=` in the URL always wins over both. The one parameter that *does* move is therefore `v`, and to move it we have to know what is in the mix — so the shortcut **fetches the watch page first** and reads the ids out of it: the page ships the whole up-next panel inline, one `playlistPanelVideoRenderer` per track (25 of them), each followed by its `videoId`. One is picked at random and opened as `watch?v=<random>&list=RDLEEx_UkHmBU&start_radio=1` — **the list id stays the seed's**, so it is still the same focus playlist, just entered at a different door; YouTube reshuffles the radio around whatever track it opens on, which is the "shuffle" that a URL cannot ask for. Parsing is a bounded scan rather than a regex over the whole page (~1.3 MB of HTML) and stops **3000 characters past each renderer marker**, so a track with no id of its own can't adopt the next one's; ids must be 11 URL-safe-base64 characters or they're dropped. **Every failure path lands on the seed URL** — offline, a consent wall, a YouTube markup change — because a shortcut that opens the right music on track 1 beats one that opens nothing. The request goes out on an **ephemeral** `URLSession` carrying a desktop browser User-Agent: YouTube serves a panel-less page to anything that doesn't look like a browser, and reading a public page must not touch the cookie jar. **The destination screen is sampled at the keypress and carried through the fetch** (`openUrlInChromeOnMouseScreen(_:on:)`) — the fetch takes a beat, and by the time the tab opens the hand has usually moved, so re-sampling would answer a question nobody asked. Changing the music means changing one constant: `FocusPlaylist.seedVideoId`, from which the `RD…` list id is derived.
- **✉️ TO DO mail to myself (⌘⌃M, `GmailCompose`)** — the write half of ⌘⌃G: it opens a **Gmail draft addressed to Victor, subject `TO DO`, with whatever is on the clipboard already in the body**, in Chrome's front-window profile. Nothing is sent — the draft sits in the browser so the note can still be edited, and a mail to yourself is a to-do item that survives every restart of everything. **The clipboard rides in the URL** (`view=cm&fs=1&to=…&su=…&body=…`), never through a simulated ⌘V: a paste has to guess when the compose window has loaded and which field owns the caret, and one field early writes the whole note into the To: box. A URL cannot miss, and the clipboard is only *read*, so ⌘V still works by hand afterwards. **No LLM, no API, no subprocess but `open -a "Google Chrome"`** — this is string building, which is why it is instant and works offline. The body is percent-encoded down to the unreserved characters, so a `&`/`=`/`#`/`+` in the clipboard can't end the parameter early. The whole URL is capped at **8000 chars** (Chrome would take far more, but the link also crosses Gmail's servers and a compose answering 400 is worse than a shortened one): past that the body is cut to fit — proportionally, since a multi-byte character encodes to 9, so cutting one at a time would loop tens of thousands of times — a `[…text scurtat…]` line is appended, and a bottom-left banner says so, because a truncated body doesn't *look* truncated and the full text is still on the clipboard. NB `openUrlInChrome` pulls the Chrome window onto the **built-in Retina** 1.5 s later, exactly as ⌘⌃G and ⌘⌃L do — and the Retina is what a venue projector mirrors, so mid-workshop this puts the clipboard on the wall.
- **📋 Snippet paste — Zoom link (⌘⌃Z) / email (⌘⌃E) / company details (⌘⌃R)** — `PasteSnippets` puts one of three fixed strings (Victor's personal Zoom room URL, his email address, the SRL's name + VAT code + address as a three-line block) on the pasteboard, fires ⌘V into whatever is focused, then **puts the previous pasteboard contents back** — a shortcut that helps with one line must not cost you the clipboard you were carrying. The restore waits 0.35 s rather than the 0.05 s `repasteLast` uses: a native text field has read the paste by then, a slow Electron one has not. Typing a Zoom link by hand in front of a room is slow and, being unreadable, a typo isn't noticed until nobody can join. NB **⌘⌃Z shadows whatever the focused app binds to ⌃⌘Z** (nothing standard does). ⌘⌃R (a client's finance department asking for the invoicing block, again) **took that combination off the 🔁 Restart menu item**, which is now click-only: one combination cannot mean two things, and the tap sees the key before AppKit's menu equivalent would.
- **🐘 The elephant in the room (⌘⌃O, `EmojiAnimator.showElephant`)** — an orange cartoon elephant with a blond comb-over and a red tie walks in from the left edge and stands in the **left half** of the built-in screen, cut out with a real alpha channel so there is no white rectangle around it. Width is claimed first (half the screen, less a 1.5% margin) and the **height then gets the final say** (≤ 62% of the screen) — on a wide screen half the width is taller than the screen is, and an elephant cropped at the knees is a bug you only ever see on the projector. The geometry is a pure `EmojiAnimator.elephantFrame(in:aspect:)`, so it is asserted in tests instead of on screen. **The letter is O, and the sheet says `trump`** — the picture wants T, and T is the empty Terminal; it wanted E next, and E is the email paste. - **🎯 Point Walkie Talkie at this terminal (⌘⌃D, `WalkieTalkieBinder`)** — press it while looking at a terminal and every later Wispr dictation is **typed into that session and submitted**, wherever the cursor is when Victor speaks. It replaces the whole `/relay` + skill + outbox-watcher ritual, which cost a trip into the terminal before the first word — the one thing the relay exists to avoid. Mechanically it `POST`s `/bind` to Walkie Talkie's loopback control surface (the first free port of **8917–8919**, the same one the Chrome element-picker uses) and the relay grabs whatever app is frontmost: a Terminal.app tab is addressed by its **tty**, a tmux client by its **`%pane`**, and anything else (VS Code, IntelliJ) by **pid** with a clipboard-paste-and-Return. The first two never touch focus; the third moves it for ~200 ms and puts it back, clipboard included. **The key lives here and not in the relay** because the relay is started per session and is down most of the time while this app is a login item — so a cold press **launches it first** (`open -g`, and the `-g` is load-bearing: the relay decides what to bind by asking which app is frontmost, so a launch that brought anything forward would spoil the very bind it enables), waits for the listener, then binds. It is also the **only** owner of the key: the relay has its own event tap and two taps claiming ⌘⌃D would both fire on one press. It takes the **first port that answers** rather than posting to all of them the way the extension does — pointing every relay on the machine at one terminal would mean every dictation arriving there two or three times. The banner names what was bound (`📍 dictation → petclinic@main · ✳ fixing the tax bug`), using the relay's own pin so the banner and the chip beside the cursor are one language. For a target the relay **cannot** interrogate before it types (VS Code, IntelliJ — a dictation there is pasted into whatever holds the caret and cannot be refused at a shell prompt) it appends **`— no shell guard`** in words: binding is the moment that fact can still change what Victor does about it, and it is said nowhere else on screen. Pressed **again on the same target** the relay ends, and the banner is then just `🎙️ relay stopped` — no folder after it: there is one relay and he has just ended it, so naming the repo only invites a reading ("stopped *for that folder*") of something with no per-folder half. **Neither half makes a sound.** The banner is already in front of him and the gesture happens several times an hour, often mid-workshop; sounds are for things that happen while he is not looking. NB ⌘⌃D **shadows the system-wide "look up in dictionary"**; ⌘⌃⌥D below is a different key, distinguished only by its ⌥, so both branches must keep testing `hasOpt`.

- **✏️ Strikethrough in PowerPoint (⌘⇧X, `PowerPointStrikethrough`)** — the one hotkey on this tap that is **scoped to a single app**: it fires only while `com.microsoft.Powerpoint` is frontmost (`currentFrontmost()`), and falls through everywhere else, because ⌘⇧X already means something in other apps. It lives here because **macOS cannot bind it**: System Settings' App Shortcuts (`NSUserKeyEquivalents`) attach a key to a *menu item title*, and PowerPoint for Mac has no Strikethrough item — all 398 items across every menu and submenu were dumped and the only hits are `Format ▸ Font…` (a dialog) and two `Replace Fonts…`. Strikethrough exists **only as a ribbon checkbox**, and unlike Word, PowerPoint ships no Tools ▸ Customize Keyboard to teach it a key. The toggle goes through PowerPoint's **own AppleScript dictionary** (`strike type` of the selection's font, `single strike` ⇄ `no strike`), *not* by AX-clicking that ribbon checkbox: the ribbon route would first have to switch the ribbon back to the Home tab — PowerPoint swings it to "Shape Format" the moment a shape is selected — and that tab flip is visible to the room mid-talk. Two selection shapes have to be handled, because `text range of selection` only answers for one of them: a caret/text selection inside a box (the usual case) and a whole shape selected, reached through `text range of text frame of shape range`. NB PowerPoint's AppleScript identifiers are touchy — a local named `st` is a parse error (`-2741`), so the script spells its variables out.

- **🔎 Cmd+scroll = terminal font zoom, at a fixed window size (`EventTapManager` + `TerminalZoomSizeLock`)** — while Terminal.app or iTerm2 is focused, Cmd+scroll is eaten and turned into the native Bigger/Smaller shortcut (Cmd+= / Cmd+-), one step per wheel notch (a `zoomAccumulator` normalises notches that emit several scroll events, and resets on direction change so a reversal responds at once). Terminals answer a font change by **keeping the character grid and resizing the window** — which throws away a placement that was deliberate (tiled by ⌘⌃A, or sized to the projector), so `TerminalZoomSizeLock` **pins the frame and writes it back** after the keystrokes settle (+0.08 s, then again at +0.35 s for a lazy relayout); the terminal reflows its rows/columns into the frame instead. The frame is captured **once per gesture** (steps < 1.2 s apart are one gesture) and read/written through the in-process **Accessibility API** — same grant as `TerminalTiler`, no Automation consent, no subprocess. It must be captured **before** the keystroke is posted, so the tap thread reads it synchronously (AX messaging timeout 0.1 s so a wedged terminal can't stall the tap into a system timeout); the pid comes from `EventTapManager`'s cached frontmost app, never from AppKit off-thread. **The one non-obvious rule is drift:** the terminal snaps our write-back down to a whole number of character cells, so the window settles a few points short of what we asked for — re-reading that at the next gesture would shrink the window by a cell *every* gesture. So the settled frame is remembered, and a window still measuring exactly it counts as untouched, keeping the **original** frame authoritative; anything else (first gesture, different window, manual drag or resize) makes what's on screen the new truth. That decision is pure and unit-tested in `TerminalZoomSizeLockPolicy.frameToPin`. Only the Cmd+scroll path is pinned — typing Cmd+= / Cmd+- directly still resizes the window the way macOS intends.
- **🔄 The mouse wheel scrolls backwards, the trackpad does not (`ScrollReversal`, 2026-09-07)** — this replaces **Scroll Reverser** (`com.pilotmoon.scroll-reverser`), uninstalled the same day, and reproduces exactly the preferences it was carrying: `InvertScrollingOn = 1`, `ReverseY` absent (its default, **on**), `ReverseX = 1` (non-default — Victor turned horizontal reversal on), `ReverseMouse` absent (default **on**), `ReverseTrackpad = 0` (non-default — he turned the trackpad **off**). Net: **negate both axes of a wheel, touch nothing a trackpad sends.** It moved in here because this app is the LaunchAgent that is up from login to shutdown; Walkie Talkie holds a session tap too but carries 2.5 GB of Whisper weights and is quit whenever that memory is wanted, and a transform that applies to *every scroll of the day* cannot live in something optional. **The trackpad is told apart by continuity, not by device** — the same test Scroll Reverser makes and the only one available, since a `CGEventTap` is handed events after the HID layer has anonymised them: a trackpad (and a Magic Mouse) scrolls continuously in pixels (`scrollWheelEventIsContinuous == 1`), a notched wheel scrolls in lines (0). That split is the point rather than an implementation detail: the system's own natural scrolling is on here (`com.apple.swipescrolldirection = 1`), and the whole reason he ran Scroll Reverser was to pull the *mouse* back out of it while leaving the two-finger gesture in. **All six delta fields are negated, not just the line delta**: an event carries the same motion three times over — `DeltaAxis` (lines), `PointDeltaAxis` (pixels) and `FixedPtDeltaAxis` (the fixed-point refinement a smooth-scrolling app reads) — and flipping only the first is the classic bug where the terminal obeys and Chrome carries on the original way. All six are read before any is written, since setting one can make the window server recompute its siblings. The event is **mutated in place**, like the ⌥ emoji layer and for its reasons: a reposted event would re-enter our own tap, and one event in is one event out, which is what a scroll's momentum and phase fields assume. **It runs BEFORE the Cmd+scroll zoom branch below, and that order is load-bearing.** Scroll Reverser was a *login item* and this app is a *LaunchAgent*, so it installed its head-inserted tap later and therefore saw scrolls first — for the whole life of the zoom feature the deltas arriving here were already reversed. `a6107c5` ("fix(scroll): invert Cmd+wheel zoom direction", pushed 20 minutes after the feature landed, from the live machine) is that fact written down: the mapping was calibrated by hand against reversed deltas. Reversing first keeps that calibration true — reversing after would have silently flipped the terminal font zoom on the day Scroll Reverser was uninstalled. **🔄 Reverse Mouse Wheel is a checkbox under 👩🏻‍💻 Extra**, beside 🟡 Cursor Glow, and it **defaults to ON** — the one row here that does. That default is the feature: this replaces a utility that was *already running*, so a fresh launch with nothing stored has to reproduce the machine as it was, and `UserDefaults.bool(forKey:)` answering **false** for a key nobody has written is precisely how a replacement like this ships silently switched off. `ScrollReversalSettings.isEnabled` therefore reads `object(forKey:) as? Bool ?? true`. It breaks *the menu is not a second cheat-sheet* on the 🔴 raw-audio row's terms rather than despite them: there is no key to teach, and no other place in the app where the state appears. **The tap reads the setting itself, on the scroll it is holding** — the toggle notifies nobody and there is no cached mirror, so the tick and the wheel cannot drift apart. That costs a `UserDefaults` lookup per scroll event, measured at **630 ns** (200k reads, `-O`), against a tap whose watchdog is measured in seconds. The corollary, worth knowing before it surprises somebody: because the reversal is a *pre-transform* sitting ahead of the zoom, unticking it also flips the terminal font zoom back.
- **⬇️ The back thumb button types Return; ⌘ + it types ⌘Return (`BackButtonEnter`, 2026-09-07)** — this replaces **LinearMouse**, uninstalled the same day, whose entire `~/.config/linearmouse/linearmouse.json` came down to those two rules on the Logitech Signature M650 L (its other two entries were LinearMouse's own defaults and did nothing). It is the button Victor submits to Claude with, so it belongs in the app that is always running. **Any other modifier passes through untouched** — LinearMouse had no rule for ⌥/⌃/⇧ or anything containing them, so neither has this, and the button goes back to being a mouse button (browsers still go back a page). **Both halves of a press we act on are swallowed** (`otherMouseUp` came back into the tap mask for this, having been dropped with the Wheel×2 gesture): an app left holding an `otherMouseUp` it never saw a down for is a real bug class. **The device scoping could not be preserved.** LinearMouse matched the M650 by USB vendor/product id; a `CGEvent` carries no device, so this applies to any mouse's back button — unobservable on a Mac with one mouse and a trackpad that has no such button. **There is no press-and-hold to detect, and it is a firmware *feature* rather than a hardware limit:** measured 2026-09-07 with a passive tap and every remapper killed, a deliberate two-second hold of either side button (back = 3, forward = 4) reaches the tap as a **4–15 ms down/up pair at the instant of release**, while the wheel on the same mouse reports a 1668 ms hold perfectly in the same window. The asymmetry is the M650 doing something deliberate — on this mouse *holding a side button is itself a gesture*, turning the wheel into horizontal scrolling, so the firmware withholds the button event until the finger comes up and leaves a tap nothing to time ([linearmouse#739](https://github.com/linearmouse/linearmouse/issues/739)). It is disableable in principle (Logi Options+, or HID++ diversion) and is **not** disabled here, so a click is all that exists. Do not build a hold on these buttons without re-measuring first. **Walkie Talkie sees this button before we do, and that is the design**: both taps are `.cgSessionEventTap` at `.headInsertEventTap`, where the most recently installed is first, and the relay starts after this login-time app; it borrows the back button as a camera shutter *while a dictation is open* and swallows it then, so the only presses reaching here are the ones it did not want. Nothing coordinates the two and nothing should. The ⌘ case sets `.maskCommand` on the posted key, which normally latches ⌘ system-wide (the trap `KeySimulator.chord` exists to avoid) and is harmless in this one case only: the user is physically holding ⌘, so the real `flagsChanged` that clears the state is already on its way. NB a synthesized Return re-enters this tap as a `keyDown`, so it still cracks the 🔥 whip while the overlay is up — which is what LinearMouse's Return did too. **Wispr Flow had the same button and won it, and the fix was in *its* settings, not here (2026-09-07).** With Wispr Flow running the Return never happened; quitting it made the button work, which is the signature of a tap ahead of ours swallowing the press — Wispr Flow is launched by hand after login, so its tap is always the newer one. Its bindings live in `~/Library/Application Support/Wispr Flow/config.json` under `prefs.user.shortcuts`, keyed by **4096 + the CGEvent button number**: `"4099": "ptt"` was the *back* button held to talk, `"4100": "popo"` the *forward* button toggling dictation on/off. The `4099` entry was deleted (from `prefs.cache.splitKeybinds` too, which mirrors the same list), leaving Wispr Flow with **forward only**; verified across a relaunch, which did not put it back. There is no way to win this from our side — re-inserting our tap to jump ahead of Wispr Flow's would also jump it ahead of Walkie Talkie's, breaking the camera-shutter split above — so a conflicting binding in another app has to be removed in that app.
