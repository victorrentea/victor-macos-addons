# Hotkeys & Launchers (EventTapManager)

Global ⌘⌃* shortcuts that open terminals, apps, docs and paste snippets, plus the clipboard/scroll niceties riding the same event tap. The hold-to-see cheat-sheets that document these keys live in `keyboard-overlays.md`; the ⌘⌃S notes shortcut lives in `session-notes.md`; ⌃P lives in `screenshots.md`.

- **🤖 Claude (⌘⌃C) / Claude with permissions bypassed (⌘⌃Q) / plain Terminal (⌘⌃T)** — all three open a Terminal in `~/workspace`, **in the quarter of the screen the cursor is in** (`MenuBarManager.screen(containing:)` + `quarter(of:on:)`): the shortcut is reached for while looking at one spot, so that spot is the answer to "where do you want this". The screen half of that rule came first — pinning the window to the built-in Retina, as this originally did, puts it on the projector mid-workshop — and the quarter followed for the same reason one scale down: `.bottomLeft` was hardcoded, so reaching for a terminal while reading the bottom-left of a screen dropped it on exactly what you were reading. **Both come from ONE `NSEvent.mouseLocation` sample**, taken in `openWorkspaceTerminal` and passed to both helpers: two separate reads can straddle a screen or quadrant edge while the hand is still moving, and the window would then be sized for one screen and placed by the geometry of another. NB the cursor is sampled when the hotkey's async block runs, a few ms after the key went down — not at the tap itself. ⌘⌃Q runs `claude --dangerously-skip-permissions`. **The command is typed into the window by `do script` (2026-08-14), which reverses the script-file design — one process is worth more than the race it closed.** For a while the command travelled in a `/tmp/victor_claude*.sh` file passed as the shell's argv, because `do script "claude"` writes its characters into a tty whose window already has keyboard focus, so a prompt Victor starts typing in that gap interleaves and the shell runs `clahelloude`; the script also drained the tty (`stty -echo` + `while read -t 0 -k 1`) so early keystrokes couldn't land in claude's startup either. What that cost was invisible until the process tree was actually read: **Terminal runs an opened document from the window's own login shell**, so every claude window carried a permanent extra zsh — `login → zsh --login → zsh -l victor_claude.sh → claude` — for a race that needs a keystroke inside the ~200 ms the window takes to appear and announces itself immediately when it happens. Typed again, the tree is `login → zsh --login → claude`. Two consequences follow from the shell being **interactive** again: `~/.zshrc` loads, so the window cds itself to `~/workspace` (no explicit `cd` to print) and aliases exist — ⌘⌃Q still spells the flag out rather than using `cx`, purely so renaming the alias can't break the hotkey. `do script` is also **synchronous with the window's creation**, so `set bounds` follows on the next line and the old `open -a Terminal` + window-count polling loop (which existed because `open` is async and would otherwise resize the *previous* window) is gone with it. The two per-repo launchers in the Extra submenu (`openDreamClaude`) were converted the same day for the same reason. ⌘⌃T opens an empty window (`do script ""`) — there is no command to garble. NB the remaining shells in a claude window are not ours: `login -pf` is Terminal's own, and claude itself spawns a zsh snapshot at startup plus one per Bash tool call. A `zsh (kiro-cli-term)` layer used to sit in there too, from Kiro CLI's shell integration; it was uninstalled (`kiro-cli integrations uninstall dotfiles`) the same day. **Each of the three then tiles that screen** (`TerminalTiler.tile(onDisplay:)`, 0.6 s after the AppleScript returns so Terminal's own `set bounds` has settled): a window already sitting in the quarter the new one just claimed would simply be covered — the whole point of opening a second terminal is to see both. Only the display the window landed on is touched; terminals on the other screens keep their frames, because the shortcut said "make room here", not "rearrange all my monitors". **Past the fourth window on a screen the extras are cascaded, not abandoned (2026-09-08)**: a screen has four readable quarters and no more, so windows 5, 6, 7… used to be left wherever they happened to sit — behind the tiled four, uncountable, and *"să le văd pe toate, câte sunt"* is the whole reason for pressing ⌘⌃A. They are now fanned over the **bottom-right** quadrant, each stepped 32 pt down-right from the previous (a Terminal title bar is ~28 pt, so a whole one shows), the last one landing flush with that quadrant's far corner — the fan therefore stays on screen and never spills over the other three tiles. The **first** step is taken immediately rather than starting flush with the corner, so the window tiled into that quadrant keeps its own title bar above the fan: the extras sit *on top of* the bottom-right window, they do not erase it. Many windows tighten the step (`min(w, h) / 2` of spread, shared out, floor 8 pt) rather than shrinking without bound. **Offset alone does not make a pile readable — offset and depth have to agree**, and that is the mistake this shipped with for one build. Frames say nothing about depth, and the extras are by construction the *back*-most windows (a neat fan hidden behind the bottom-right tile is no better than no fan), so ⌘⌃A now walks the whole screen with `kAXRaiseAction` in **slot order — top-left, top-right, bottom-left, bottom-right, then the fan from its shallowest slot to its deepest**, the last one raised ending on top. A title bar sits at the **top** of its window, so the window stepped further down-right has to be the one in front; the first cut raised the fan the other way round and covered every title bar behind it but for a 32 pt sliver at the far right — *"restul sunt una sub alta"*, fanned in geometry and a single window to the eye. **Re-tiling moves nothing** (2026-09-08: *"le cam face shuffle"*): slots used to go to the four *front-most* windows, and since raising the fan makes the fan front-most, every press swapped the fan with the tiles. Which window gets which slot is now decided by **where it currently sits** — greedy nearest-pair matching on window **origin and size**, not centre, because a fan slot and the quadrant it lies on share a centre almost exactly while their origins differ by a whole step. A window already on its slot matches at cost 0 and takes it before anything else is considered, so ⌘⌃A twice in a row is a no-op (verified live: two consecutive tiles, identical frames *and* identical z-order, per window title). **Depth and the keyboard are the same thing in Terminal** — measured, both directions: `kAXRaiseAction` makes a window key, and setting `AXMain`/`AXFocused` on a back window brings it straight to the front. "Fan on top" and "keep typing where I was" therefore cannot both be had, and the last window raised is the one that ends up focused — so **the walk does not get the last word: the window that was focused is raised after it, always** (*"în niciun caz să nu-mi schimbi focusul din terminalul activ în altul când faci tile"*). Arranging windows is not a reason to send the next keystrokes to another terminal, and it is the same rule that keeps ⌘⌃C's brand-new window under the fingers when the open tiles the screen a moment later. It is free in the ordinary case — the focused window is one of the three quadrants the fan never reaches, so raising it covers nothing. The single case where the two rules collide is the focused window being the **bottom-right tile**: putting the keyboard back there covers the fan lying on it, and the keyboard wins. Verified live both ways: focus on a plain tile and focus on a fan window each survive a tile untouched. All of it is pure and unit-tested in `TerminalTileLayout` (`TerminalTileLayoutTests`), leaving `TerminalTiler` as the Accessibility plumbing alone. NB ⌘⌃Q **shadows macOS's own ⌃⌘Q "Lock Screen"**: the `.cgSessionEventTap` sees the key first and swallows it, so the Mac no longer locks on that combination.

- **🎧 Focus playlist (⌘⌃F, `FocusPlaylist`)** — opens Victor's YouTube focus mix (`RDLEEx_UkHmBU`) in Victor's own Chrome profile (YouTube Premium, no ads), **on a random track**, as a tab on the screen the mouse is on (`openUrlInChromeOnMouseScreen`, so it never lands on the projected Retina). F is for *focus*: the word names what the music is for, not the site it comes from — "youtube" would have described three other keys equally well. **The random start has to be built by hand, because YouTube offers no lever for it**: on an `RD…` radio list `&index=` is ignored (`watch?list=RD…&index=12` and `index=1` both resolve to the same video — measured, not assumed), `&shuffle=1` is ignored outright, and a `v=` in the URL always wins over both. The one parameter that *does* move is therefore `v`, and to move it we have to know what is in the mix — so the shortcut **fetches the watch page first** and reads the ids out of it: the page ships the whole up-next panel inline, one `playlistPanelVideoRenderer` per track (25 of them), each followed by its `videoId`. One is picked at random and opened as `watch?v=<random>&list=RDLEEx_UkHmBU&start_radio=1` — **the list id stays the seed's**, so it is still the same focus playlist, just entered at a different door; YouTube reshuffles the radio around whatever track it opens on, which is the "shuffle" that a URL cannot ask for. Parsing is a bounded scan rather than a regex over the whole page (~1.3 MB of HTML) and stops **3000 characters past each renderer marker**, so a track with no id of its own can't adopt the next one's; ids must be 11 URL-safe-base64 characters or they're dropped. **Every failure path lands on the seed URL** — offline, a consent wall, a YouTube markup change — because a shortcut that opens the right music on track 1 beats one that opens nothing. The request goes out on an **ephemeral** `URLSession` carrying a desktop browser User-Agent: YouTube serves a panel-less page to anything that doesn't look like a browser, and reading a public page must not touch the cookie jar. **The destination screen is sampled at the keypress and carried through the fetch** (`openUrlInChromeOnMouseScreen(_:on:)`) — the fetch takes a beat, and by the time the tab opens the hand has usually moved, so re-sampling would answer a question nobody asked. Changing the music means changing one constant: `FocusPlaylist.seedVideoId`, from which the `RD…` list id is derived.
- **✉️ TO DO mail to myself (menu row only since 2026-09-08, `GmailCompose`)** — **it had ⌘⌃M and lost it to the Reminder mail below**: the two were one gesture (clipboard → a mail to myself) split over two keys by a difference — draft or send — that nobody weighs mid-sentence, and the half that finishes by itself won. It keeps the menu row **✉️ Draft TO DO mail with clipboard** rather than being deleted, because drafting is still the right shape when the note needs editing before it goes; a click is a fine price for the rarer of the two, and the doc below (in particular the Chrome-onto-the-Retina note) is why it is the rarer one mid-workshop. It opens a **Gmail draft addressed to Victor, subject `TO DO`, with whatever is on the clipboard already in the body**, in Victor's own Chrome profile. Nothing is sent — the draft sits in the browser so the note can still be edited, and a mail to yourself is a to-do item that survives every restart of everything. **The clipboard rides in the URL** (`view=cm&fs=1&to=…&su=…&body=…`), never through a simulated ⌘V: a paste has to guess when the compose window has loaded and which field owns the caret, and one field early writes the whole note into the To: box. A URL cannot miss, and the clipboard is only *read*, so ⌘V still works by hand afterwards. **No LLM, no API, no subprocess but the one that hands Chrome the URL** — this is string building, which is why it is instant and works offline. The body is percent-encoded down to the unreserved characters, so a `&`/`=`/`#`/`+` in the clipboard can't end the parameter early. The whole URL is capped at **8000 chars** (Chrome would take far more, but the link also crosses Gmail's servers and a compose answering 400 is worse than a shortened one): past that the body is cut to fit — proportionally, since a multi-byte character encodes to 9, so cutting one at a time would loop tens of thousands of times — a `[…text scurtat…]` line is appended, and a bottom-left banner says so, because a truncated body doesn't *look* truncated and the full text is still on the clipboard. NB `openUrlInChrome` pulls the Chrome window onto the **built-in Retina** 1.5 s later, exactly as ⌘⌃G and ⌘⌃L do — and the Retina is what a venue projector mirrors, so mid-workshop this puts the clipboard on the wall.
- **📤 Reminder mail to myself (⌘⌃M since 2026-09-08, was ⌘⌃P, `ReminderMail` / `ReminderMailer`)** — whatever is on the clipboard — **a picture, some text, or both** — is **sent** to `victorrentea@gmail.com`, subject `Reminder`, over AgentMail's REST API. **Sent, not drafted: that is the whole difference from the ✉️ draft it displaced.** The draft opens a Gmail compose window and waits for a human; this key is finished the moment it is released, which is what makes it usable one-handed mid-sentence in front of a room — and what makes the banner afterwards a receipt rather than a progress bar (it reports the real HTTP outcome, never "probably sent"). **The letter is M for *mail*, and it moved there on 2026-09-08.** It sat on ⌘⌃P for the neat reason that ⌃P *fills* the clipboard with a screenshot and ⌘⌃P *posted* whatever was in it — one more modifier, the next step of the same gesture — but that reading only works from the screenshot's side; from the mail's side, M is where the hand goes, and P was the only free letter for the 🤖 prompt key that now owns it. Nothing about ⌃P changed: its branch requires `!hasCmd`, and `screenshotKeyDownAt` is only ever set there, so releasing ⌘⌃P cannot take a screenshot either. **Autorepeat is excluded**: every other ⌘⌃ key is harmless to repeat, but a held ⌘⌃M would mail the same clipboard once per repeat into a real inbox.
  - **No LLM, no agent, no tokens** — `JSONSerialization` plus one `POST` to `.../v0/inboxes/{inbox}/messages/send`, on the same `AGENTMAIL_API_KEY` the 📬 `FluxInboxPoller` already loads, driven in the **sending** direction. **AgentMail is the sender, Gmail only ever the destination.** With no key in the secrets file the shortcut is simply not wired and says so once, at launch, instead of failing on every press.
  - **What counts as "a picture"** — three sources, in order of fidelity: `public.png` (what ⌃P and macOS screenshots leave), then `public.tiff` re-encoded to PNG (what most apps put there when you copy an image — raw TIFF is refused inline by several mail clients), then an **image file copied in Finder**, which arrives as a *URL, not pixels*, and without that branch would have mailed its own path as text. When the file-URL branch fires, a body that is just that path/filename is dropped: the picture is the reminder, the path is noise — but a real note copied alongside it survives. Both halves are always kept when both exist; copying from a web page or a spreadsheet cell yields a picture *and* text, and choosing one would silently discard the half you meant.
  - **The picture is inline, not an attachment to click** — `content_disposition: inline` plus a `content_id` the HTML part references as `cid:clipboard`. The attachment keys are **snake_case** (`content_type`, `content_id`, `content_disposition`); AgentMail ignores camelCase **in silence**, and an ignored `content_id` turns the inline image into a dangling `cid:`. An image-only reminder still gets a plain-text part, because clients that prefer `text/plain` would otherwise render it blank — which looks like a failure, not like a picture.
  - **The subject is searchable** — always `Reminder`, plus the clipboard's first non-empty line (60 chars, then `…`) when there is one, so `subject:Reminder` in Gmail finds the whole set while a notification still says which one. Only the first line is ever used, so a `\n` in the clipboard cannot become a second header.
  - **Sizes** — AgentMail caps the whole request at 6 MB and base64 adds a third, so attachments are held under 4 MB: a retina full-screen PNG (~8 MB) is re-encoded to JPEG at 0.7, then 0.4, then 0.2. **Quality is spent before pixels on purpose** — a reminder is read once, so artefacts cost nothing, while a screenshot scaled far enough to fit stops being legible, which is usually the entire content. If nothing fits, it is sent anyway and AgentMail's own error reaches the banner, rather than this code inventing a verdict. Body text is capped at 100 KB.
  - The clipboard is **only ever read**, so ⌘V still works afterwards, and a failed send is retried by pressing the key again — which the banner says. The recipient is **hardcoded**, like `FluxAgentLauncher`'s `TRUSTED_SENDER`: no clipboard content can choose an address, so a copied page cannot turn this into an outbound mail to someone else. The payload is built as a dictionary handed to `JSONSerialization`, never interpolated, so quotes and backslashes in the clipboard can't reshape the request. Headless test hook: `GET /test/reminder` on 55123 takes the same path without a keypress. The menu row **📤 Mail clipboard to myself** advertises ⌘⌃M; the event tap swallows the key before AppKit could match the equivalent, so the row cannot fire a second send.
- **🤖 Selection → agent prompt (⌘⌃P since 2026-09-08, `SessionNotesAppender.sendSelectionAsPrompt`)** — the selected text (or, when nothing answers, the clipboard) is appended to the session notes as a **prompt** line, stamped 🤖, which is what makes it appear in the participants' **Prompts** tab — the daemon builds that tab by reading 🤖 lines back out of the notes file, so there is no second store and nothing to keep in sync. **This is the manual door into a list that is otherwise filled automatically.** The interception offers a hover-pill for prompts it sees; prompts typed where it isn't watching never reach the room at all, and that gap is the entire reason for the key: select the text, press it, and it is in the list beside the intercepted ones. **Same capture as ⌘⌃S, different shelf** — it *is* `copySelectionAndAppend`, parameterised by marker: Accessibility first (`SelectionReader`, no keystroke, clipboard untouched), a simulated ⌘C only once the hotkey's own modifiers are off the keyboard, the clipboard as the last answer — see `session-notes.md` for why that order is load-bearing. - **🎯 Point Walkie Talkie at this terminal (⌘⌃D, `WalkieTalkieBinder`)** — press it while looking at a terminal and every later Wispr dictation is **typed into that session and submitted**, wherever the cursor is when Victor speaks. It replaces the whole `/relay` + skill + outbox-watcher ritual, which cost a trip into the terminal before the first word — the one thing the relay exists to avoid. Mechanically it `POST`s `/bind` to Walkie Talkie's loopback control surface (the first free port of **8917–8919**, the same one the Chrome element-picker uses) and the relay grabs whatever app is frontmost: a Terminal.app tab is addressed by its **tty**, a tmux client by its **`%pane`**, and anything else (VS Code, IntelliJ) by **pid** with a clipboard-paste-and-Return. The first two never touch focus; the third moves it for ~200 ms and puts it back, clipboard included. **The key lives here and not in the relay** because the relay is started per session and is down most of the time while this app is a login item — so a cold press **launches it first** (`open -g`, and the `-g` is load-bearing: the relay decides what to bind by asking which app is frontmost, so a launch that brought anything forward would spoil the very bind it enables), waits for the listener, then binds. It is also the **only** owner of the key: the relay has its own event tap and two taps claiming ⌘⌃D would both fire on one press. It takes the **first port that answers** rather than posting to all of them the way the extension does — pointing every relay on the machine at one terminal would mean every dictation arriving there two or three times. The banner names what was bound (`📍 dictation → petclinic@main · ✳ fixing the tax bug`), using the relay's own pin so the banner and the chip beside the cursor are one language. For a target the relay **cannot** interrogate before it types (VS Code, IntelliJ — a dictation there is pasted into whatever holds the caret and cannot be refused at a shell prompt) it appends **`— no shell guard`** in words: binding is the moment that fact can still change what Victor does about it, and it is said nowhere else on screen. Pressed **again on the same target** the relay ends, and the banner is then just `🎙️ relay stopped` — no folder after it: there is one relay and he has just ended it, so naming the repo only invites a reading ("stopped *for that folder*") of something with no per-folder half. **Neither half makes a sound.** The banner is already in front of him and the gesture happens several times an hour, often mid-workshop; sounds are for things that happen while he is not looking. - **✏️ Strikethrough in PowerPoint (⌘⇧X, `PowerPointStrikethrough`)** — the one hotkey on this tap that is **scoped to a single app**: it fires only while `com.microsoft.Powerpoint` is frontmost (`currentFrontmost()`), and falls through everywhere else, because ⌘⇧X already means something in other apps. Strikethrough exists **only as a ribbon checkbox**, and unlike Word, PowerPoint ships no Tools ▸ Customize Keyboard to teach it a key. The toggle goes through PowerPoint's **own AppleScript dictionary** (`strike type` of the selection's font, `single strike` ⇄ `no strike`), *not* by AX-clicking that ribbon checkbox: the ribbon route would first have to switch the ribbon back to the Home tab — PowerPoint swings it to "Shape Format" the moment a shape is selected — and that tab flip is visible to the room mid-talk. Two selection shapes have to be handled, because `text range of selection` only answers for one of them: a caret/text selection inside a box (the usual case) and a whole shape selected, reached through `text range of text frame of shape range`. NB PowerPoint's AppleScript identifiers are touchy — a local named `st` is a parse error (`-2741`), so the script spells its variables out.

- **🔎 Cmd+scroll = terminal font zoom, on the window under the pointer, at a fixed window size (`EventTapManager` + `TerminalZoomTarget` + `TerminalZoomSizeLock`)** — while Terminal.app or iTerm2 is focused, Cmd+scroll is eaten and turned into the native Bigger/Smaller shortcut (Cmd+= / Cmd+-), one step per wheel notch (a `zoomAccumulator` normalises notches that emit several scroll events, and resets on direction change so a reversal responds at once). **The step lands on the terminal window the mouse is over, not the one being typed in** (2026-09-07) — with six terminals tiled across two screens, the window you are pointing at is the one you mean, and the focused one was a coin flip. `TerminalZoomTargeting.resolve` asks the window server for the on-screen list (one local call, front-to-back, so a hung app cannot slow it down), takes the first **layer-0** window containing the pointer — a menu, a panel or one of this app's own click-through overlays is neither a target nor a blocker — and matches its frame against the app's AX windows to get an element; **anything else falls back to the focused window**, which is what the gesture did before: the pointer over Chrome, over the desktop, or over the *other* terminal app. **Aiming means moving the keyboard, and there is no way around that.** A terminal applies Bigger/Smaller to whichever of *its* windows holds the keyboard, so `TerminalZoomSizeLock.borrowFocus` sets AXMain+AXFocused on the target before the keystroke and **gives the borrow back 0.6 s after the last notch** — after the frame write-backs, and only if that window still holds the keyboard, since a click elsewhere in the meantime makes the return a focus *steal*. Dragging the pointer across three terminals mid-gesture returns to where it started, not to the second one it passed over. Measured on 2026-09-07, with Terminal.app **inactive** all three alternatives report success and change nothing: keys posted straight into the process (`CGEventPostToPid`), an AX press of *View ▸ Bigger*, and setting `AXFocused` on the window (`rc = 0`, and the app's focused window afterwards is still the old one) — an inactive app has no key window, so a font command has nothing to apply to. That is why the pointer only ever retargets **within the active terminal app**: reaching a window of an inactive app would mean activating that app mid-scroll. Terminals answer a font change by **keeping the character grid and resizing the window** — which throws away a placement that was deliberate (tiled by ⌘⌃A, or sized to the projector), so `TerminalZoomSizeLock` **pins the frame and writes it back** after the keystrokes settle (+0.08 s, then again at +0.35 s for a lazy relayout); the terminal reflows its rows/columns into the frame instead. The frame is captured **once per gesture** (steps < 1.2 s apart are one gesture, and the pointer moving onto a *different* terminal window starts a new one) and read/written through the in-process **Accessibility API** (`AXWindows`, one cached app element per pid, 0.1 s messaging timeout) — same grant as `TerminalTiler`, no Automation consent, no subprocess. It must be captured **before** the keystroke is posted, so the tap thread reads it synchronously (AX messaging timeout 0.1 s so a wedged terminal can't stall the tap into a system timeout); the pid comes from `EventTapManager`'s cached frontmost app, never from AppKit off-thread. **The one non-obvious rule is drift:** the terminal snaps our write-back down to a whole number of character cells, so the window settles a few points short of what we asked for — re-reading that at the next gesture would shrink the window by a cell *every* gesture. So the settled frame is remembered, and a window still measuring exactly it counts as untouched, keeping the **original** frame authoritative; anything else (first gesture, different window, manual drag or resize) makes what's on screen the new truth. That decision is pure and unit-tested in `TerminalZoomSizeLockPolicy.frameToPin`, as the targeting is in `TerminalZoomTargetPolicy.choose`. Only the Cmd+scroll path is pinned — typing Cmd+= / Cmd+- directly still resizes the window the way macOS intends.
- **🔄 The mouse wheel scrolls backwards, the trackpad does not (`ScrollReversal`, 2026-09-07)** — this replaces **Scroll Reverser** (`com.pilotmoon.scroll-reverser`), uninstalled the same day, and reproduces exactly the preferences it was carrying: `InvertScrollingOn = 1`, `ReverseY` absent (its default, **on**), `ReverseX = 1` (non-default — Victor turned horizontal reversal on), `ReverseMouse` absent (default **on**), `ReverseTrackpad = 0` (non-default — he turned the trackpad **off**). Net: **negate both axes of a wheel, touch nothing a trackpad sends.** It moved in here because this app is the LaunchAgent that is up from login to shutdown; Walkie Talkie holds a session tap too but carries 2.5 GB of Whisper weights and is quit whenever that memory is wanted, and a transform that applies to *every scroll of the day* cannot live in something optional. **The trackpad is told apart by continuity, not by device** — the same test Scroll Reverser makes and the only one available, since a `CGEventTap` is handed events after the HID layer has anonymised them: a trackpad (and a Magic Mouse) scrolls continuously in pixels (`scrollWheelEventIsContinuous == 1`), a notched wheel scrolls in lines (0). That split is the point rather than an implementation detail: the system's own natural scrolling is on here (`com.apple.swipescrolldirection = 1`), and the whole reason he ran Scroll Reverser was to pull the *mouse* back out of it while leaving the two-finger gesture in. **All six delta fields are negated, not just the line delta**: an event carries the same motion three times over — `DeltaAxis` (lines), `PointDeltaAxis` (pixels) and `FixedPtDeltaAxis` (the fixed-point refinement a smooth-scrolling app reads) — and flipping only the first is the classic bug where the terminal obeys and Chrome carries on the original way. All six are read before any is written, since setting one can make the window server recompute its siblings. The event is **mutated in place**, like the ⌥ emoji layer and for its reasons: a reposted event would re-enter our own tap, and one event in is one event out, which is what a scroll's momentum and phase fields assume. **It runs BEFORE the Cmd+scroll zoom branch below, and that order is load-bearing.** Scroll Reverser was a *login item* and this app is a *LaunchAgent*, so it installed its head-inserted tap later and therefore saw scrolls first — for the whole life of the zoom feature the deltas arriving here were already reversed. `a6107c5` ("fix(scroll): invert Cmd+wheel zoom direction", pushed 20 minutes after the feature landed, from the live machine) is that fact written down: the mapping was calibrated by hand against reversed deltas. Reversing first keeps that calibration true — reversing after would have silently flipped the terminal font zoom on the day Scroll Reverser was uninstalled. **🔄 Reverse Mouse Wheel is a checkbox under 👩🏻‍💻 Extra**, beside 🟡 Cursor Glow, and it **defaults to ON** — the one row here that does. That default is the feature: this replaces a utility that was *already running*, so a fresh launch with nothing stored has to reproduce the machine as it was, and `UserDefaults.bool(forKey:)` answering **false** for a key nobody has written is precisely how a replacement like this ships silently switched off. `ScrollReversalSettings.isEnabled` therefore reads `object(forKey:) as? Bool ?? true`. It breaks *the menu is not a second cheat-sheet* on the 🔴 raw-audio row's terms rather than despite them: there is no key to teach, and no other place in the app where the state appears. **The tap reads the setting itself, on the scroll it is holding** — the toggle notifies nobody and there is no cached mirror, so the tick and the wheel cannot drift apart. That costs a `UserDefaults` lookup per scroll event, measured at **630 ns** (200k reads, `-O`), against a tap whose watchdog is measured in seconds. The corollary, worth knowing before it surprises somebody: because the reversal is a *pre-transform* sitting ahead of the zoom, unticking it also flips the terminal font zoom back.

- **⬇️ The back thumb button types Return; ⌘ + it types ⌘Return (`BackButtonEnter`, 2026-09-07)** — this replaces **LinearMouse**, uninstalled the same day, whose entire `~/.config/linearmouse/linearmouse.json` came down to those two rules on the Logitech Signature M650 L (its other two entries were LinearMouse's own defaults and did nothing). It is the button Victor submits to Claude with, so it belongs in the app that is always running. **Any other modifier passes through untouched** — LinearMouse had no rule for ⌥/⌃/⇧ or anything containing them, so neither has this, and the button goes back to being a mouse button (browsers still go back a page). **Both halves of a press we act on are swallowed** (`otherMouseUp` came back into the tap mask for this, having been dropped with the Wheel×2 gesture): an app left holding an `otherMouseUp` it never saw a down for is a real bug class. **The device scoping could not be preserved.** LinearMouse matched the M650 by USB vendor/product id; a `CGEvent` carries no device, so this applies to any mouse's back button — unobservable on a Mac with one mouse and a trackpad that has no such button. **There is no press-and-hold to detect, and it is a firmware *feature* rather than a hardware limit:** measured 2026-09-07 with a passive tap and every remapper killed, a deliberate two-second hold of either side button (back = 3, forward = 4) reaches the tap as a **4–15 ms down/up pair at the instant of release**, while the wheel on the same mouse reports a 1668 ms hold perfectly in the same window. The asymmetry is the M650 doing something deliberate — on this mouse *holding a side button is itself a gesture*, turning the wheel into horizontal scrolling, so the firmware withholds the button event until the finger comes up and leaves a tap nothing to time ([linearmouse#739](https://github.com/linearmouse/linearmouse/issues/739)). It is disableable in principle (Logi Options+, or HID++ diversion) and is **not** disabled here, so a click is all that exists. Do not build a hold on these buttons without re-measuring first. **Walkie Talkie does not reliably see this button before we do, so the Return is stamped (2026-09-08)**: both taps are `.cgSessionEventTap` at `.headInsertEventTap`, where the most recently installed is first, and the assumption was that the relay — started after this login-time app — is ahead, borrowing the back button as a camera shutter *while a dictation is open*. That holds only until this app is rebuilt and restarted, which is what happens after every change to it. On 2026-09-08 it was the newer tap (relay up 22:14, this app 22:37), so every press became a Return before the relay saw a mouse button: no shot, and the Enter leaked to whatever was in front (in Chrome it scrolled the page). The relay has a second branch for exactly this order — a Return arriving mid-dictation *is* the shutter — but it identified that Return by the source process's name, `LinearMouse`, and a name cannot work for us: this app posts Returns for other reasons (`KeySimulator`) and those really do mean Enter. So `post` stamps `eventSourceUserData` with `backButtonStamp` (`0x7774_4241_434B_0000`) and the relay keys on that instead. **The literal is duplicated in `HotkeyTap.swift` in the walkie-talkie repo and must not drift.** Restart order no longer matters: whichever tap is first, the shot is taken exactly once. The ⌘ case sets `.maskCommand` on the posted key, which normally latches ⌘ system-wide (the trap `KeySimulator.chord` exists to avoid) and is harmless in this one case only: the user is physically holding ⌘, so the real `flagsChanged` that clears the state is already on its way. NB a synthesized Return re-enters this tap as a `keyDown`, so it still cracks the 🔥 whip while the overlay is up — which is what LinearMouse's Return did too. **Wispr Flow had the same button and won it, and the fix was in *its* settings, not here (2026-09-07).** With Wispr Flow running the Return never happened; quitting it made the button work, which is the signature of a tap ahead of ours swallowing the press — Wispr Flow is launched by hand after login, so its tap is always the newer one. Its bindings live in `~/Library/Application Support/Wispr Flow/config.json` under `prefs.user.shortcuts`, keyed by **4096 + the CGEvent button number**: `"4099": "ptt"` was the *back* button held to talk, `"4100": "popo"` the *forward* button toggling dictation on/off. The `4099` entry was deleted (from `prefs.cache.splitKeybinds` too, which mirrors the same list), leaving Wispr Flow with **forward only**; verified across a relaunch, which did not put it back. There is no way to win this from our side — re-inserting our tap to jump ahead of Wispr Flow's would also jump it ahead of Walkie Talkie's, breaking the camera-shutter split above — so a conflicting binding in another app has to be removed in that app.
