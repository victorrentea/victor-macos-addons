# Victor macOS Addons

macOS utilities for live training workshops, running on the trainer's Mac.
Single menu bar app (💬 icon) provides all functionality.

## Architecture

- **Single Swift process**: `VictorAddons` is the main application combining menu bar UI and overlay functionality
- **LaunchAgent**: `ro.victorrentea.macos-addons.plist` — starts on login, no KeepAlive
- **Components**: All features run in same process with direct method calls (no IPC needed)

## Features

### Menu Bar (MenuBarManager)
Menu bar app (💬 icon) with the following features:

**Active features:**
- **💬 Transcribing** — Whisper live transcription runs **automatically whenever the Mac is on AC power, and pauses on battery**. There is no schedule, no workday window, and **no manual start/stop** — the only input that matters is the power source. The single, tiny `TranscriptionController` owns this: on AC it starts Whisper (if not already running) and a **60s heartbeat** restarts it if the process died (crash/OOM) while still plugged in; on battery it stops Whisper. On AC→battery it shows a "paused on battery" banner; on battery→AC a "resumed on AC" banner and Whisper restarts automatically (unlike the old model, AC restoration **does** auto-resume). It captures **two channels at once** (`whisper_runner.py`): your mic (the "selected device", auto-picked by priority Wireless Mic → Room Speakerphone → XLR → Bose → MacBook, overridable in the menu submenu) written as `Victor:`, and the **audience from the `From Zoom` loopback** written as `Audience:`. The menu item is a **read-only status row** (💬 Transcribing / Off – On Battery / Transcribing (off) while momentarily down) that opens the **mic-source picker submenu** — no Start/Stop, no ⌘⌃T hotkey, no 🔒 lock. The menu-bar icon is the live status: source emoji while running, leaf on battery, blinking red stop icon when on AC but Whisper isn't running (an error worth flagging, at any hour). The built-in mic's glyph is the **Apple logo** (U+F8FF, the bitten apple — "this Mac", not "a laptop"), not 💻: `MenuBarManager.glyphOverrides` swaps only what is *drawn*, because 💻 is the **wire value** whisper emits (`_ME_PATTERNS`) and every lookup — `availableSources`, the submenu checkmark — is string equality on it. It is also the only *monochrome* source glyph, so it is drawn with an explicit ink colour resolved from the surface's `effectiveAppearance` (white on dark, black on light) and re-baked on `AppleInterfaceThemeChangedNotification`; menu-item *titles* need no tint (AppKit draws them in the menu's own label colour). It is drawn **×1.25 larger** than an emoji at the same point size (`monochromeGlyphScale`): a text glyph sits inside its em-box and the apple fills far less of it — measured in an 18×18 icon, 💻 inks the full 18×18 while  inks only 10.5×13, which simply reads as a smaller icon. ×1.25 gets it to 13×16 and still clears both boxes we draw into (18×18 menu bar, 16×16 menu item); ×1.4 clips. The system font carries U+F8FF directly — "Apple Symbols", despite the name, does **not** (verified with `CTFontGetGlyphsForCharacters`; it only rendered through fallback).

  **Alive ≠ working — the output watchdog.** The 60 s heartbeat used to check only that the process existed, which is not the same as it doing anything: a capture thread inside whisper can die on its own while the process, its other thread and the PID all stay healthy, so the icon reads 💬 and not one word gets transcribed for hours (observed 2026-07-28: 4 h of nothing). The heartbeat therefore also watches the **output** — when whisper is alive on AC but no *speech* has landed for 5 min it is killed and restarted (`TranscriptionController.shouldForceRestart`, pure + unit-tested), gated by a 5 min warm-up since the last start (a fresh whisper is silent while it loads its model) and a 10 min floor between forced restarts (if a restart didn't fix it, looping is worse than the silence). "Speech" is `TranscriptActivity`, not the file's mtime: whisper writes `--- Victor → 💻 ---` device markers into the same transcript, and each one bumped the mtime and so granted another full staleness window — which is exactly why the 😶😶😶 warning kept clearing itself while nothing was being transcribed. Only `[HH:MM] Speaker: text` lines count, and `TranscriptionWatcher` now uses the same probe. **Never interpolate the silence value directly**: it is `.infinity` when nothing has been transcribed all day — the likeliest case when the watchdog fires — and `Int(.infinity)` *traps*, which crashed the whole app the first two times this triggered (2026-07-29, `EXC_BREAKPOINT` in `heartbeatTick`), before the restart it was announcing. Go through `TranscriptionController.describe`.
- **⌨️ Hold-to-see cheat-sheets (`KeymapOverlay`)** — holding a modifier long enough to be *asking* rather than *typing* draws a keyboard on the secondary screen. Two sheets, one renderer, one hold delay (`KeymapHoldCoordinator.delay`: 0.3 s multi-monitor, 1.0 s single, since on one screen the sheet covers what you're doing): **⌥ / ⌥⇧** show the emoji/character each key emits, parsed live out of the active `.keylayout`; **⌘⌃** shows what this app's own ⌘⌃ shortcuts *do*, one word per key (`terminal`, `claude` on **both C and Q** — Q is the permissions-bypassed `cx` —, `notes`, `wispr🎙️`, `tile`, `SRL`, `zoom`, `email`, `catalog`, `todo`). Three keys answer with a **picture instead of a word**, because a mark is recognised faster than the name of the thing: **L = 📅** (calendar), **G = the Gmail logo** and **N = the Google Docs logo** (the "notes" doc itself — the mark *is* the destination, where S's `notes` is the act of sending something there). The two emoji stay in `CommandControlShortcuts.labels` and are detected by the pure `KeymapOverlayRenderer.isPictogram` — a label that is *nothing but* emoji is drawn big and centred in the whole payload area instead of being shrunk to word size at the bottom (`wispr🎙️` is a word that merely *contains* one, so it must not qualify). The Gmail and Docs marks are bundled PNGs (`Resources/gmail-logo.png`, `Resources/gdocs-logo.png`, listed in `CommandControlShortcuts.artworkNames`, loaded through `artworkImages()`) drawn **straight onto the key with its own transparency intact — no white plate behind it**: every key on this sheet is one flat black, so a white card under a single one is the loudest thing on the whole keyboard. The mark survives the dark background because the M *is* the coloured part; the envelope body Gmail normally paints white simply reads as key. A key carrying artwork counts as **bound** even though its `labels` entry is absent, so `boundKeyCodes` (labels ∪ artwork) — not `labels.keys` — is what the sync test asserts. Four keys also carry a small **corner accent** (`CommandControlShortcuts.accents`) in the top-right, opposite the base letter: **E = @**, **Z = 🔗**, **S = 🚀**, **R = 📋**, **K = 📕** and **M = ✉️**. Their words ("email", "zoom", "notes", "SRL", "catalog", "todo") are nouns — the *thing*, not what happens to it — so the mark supplies the missing verb a beat faster: 🚀 says the selection is launched into the notes, 📋 that the SRL details are pasted rather than opened, 📕 which book "catalog" means; it is drawn at 28pt against the letter's 42 precisely so it reads as a hint on the key and not as a second key label. A test asserts every accented key is one that's actually bound — an accent on a dimmed key would decorate nothing. Which sheet a combination asks for is the pure, unit-tested `KeymapHoldCoordinator.sheet` — deliberately exact, so the mixed combos that are themselves shortcuts (⌘⌃⌥D dark mode, ⌃⌥V notes) show nothing rather than guess. The word sheet renders through the same `KeymapOverlayRenderer` in `.word` style: the letter shrinks to the top-left corner to make room, the word wraps across the bottom at a size chosen by its length (`wordFontSize` — word-wrap cannot break a single word, so an oversized font spills over the key border instead of wrapping), and **keys with nothing bound are dimmed to 22% while bound ones keep the full-brightness border**, so the eye lands only on what's live. The ⌘⌃ image is built **in the controller's `init`, not from the layout file**: those are app shortcuts, not characters, so a failure to locate the `.keylayout` must not take the shortcut sheet down with it (which also means `images` is never empty — the layout retry now asks `images[.option] == nil`). Pressing any key under either modifier drops the overlay (`keyDownWhileModifierHeld`): the hold turned out to be a real shortcut. `CommandControlShortcuts.labels` is the map and **must stay in sync with the ⌘⌃ branches in `EventTapManager`**; a test asserts the exact key-code set. Two deliberate exceptions to that rule, both documented in the map: **⌘⌃W is on the sheet but NOT bound here** — it is Wispr Flow's "paste transcript", and the sheet answers "what does this combination do on this Mac", so an empty key would be the wrong answer (the tap's ⌃W → 🔥 Whip branch requires `!hasCmd`, so ⌘⌃W passes straight through); and **⌘⌃V is bound but NOT on the sheet** — "paste" now means ⌘⌃W to the hand, and two keys reading the same word makes the reader pick wrong at speed. The **Emoji Overlay** menu item toggles both sheets.
- **Emotional 🥹 Paste (⌘⌃V)** — AI-powered text cleanup via Claude Haiku; intercepts Cmd+V to capture clipboard, Cmd+Ctrl+V cleans and re-pastes
- **📝 Selection-or-clipboard → session notes (⌘⌃S)** — `SessionNotesAppender.copySelectionAndAppend` simulates ⌘C and, if the pasteboard's `changeCount` moved, appends the selection; if it did **not** move (the app no-op'd the copy = nothing was selected) it falls back to whatever is already on the clipboard. One key covers both because at the moment of pressing they are one intent — "put THIS in the notes" — and remembering which of two shortcuts matches the current state of the screen is the friction that stopped it being used mid-talk. Selection wins when both exist: it is the fresher of the two. Moved off **⌃⌥C** so it lands on the ⌘⌃ cheat-sheet (`notes`). ⌃⌥V (clipboard-only) and its menu item stay — a menu *click* can never capture the previous app's selection, so the clipboard entry is the only one that works from the menu.
- **🤖 Claude (⌘⌃C) / Claude with permissions bypassed (⌘⌃Q) / plain Terminal (⌘⌃T)** — all three open a Terminal in `~/workspace`, **in the quarter of the screen the cursor is in** (`MenuBarManager.screen(containing:)` + `quarter(of:on:)`): the shortcut is reached for while looking at one spot, so that spot is the answer to "where do you want this". The screen half of that rule came first — pinning the window to the built-in Retina, as this originally did, puts it on the projector mid-workshop — and the quarter followed for the same reason one scale down: `.bottomLeft` was hardcoded, so reaching for a terminal while reading the bottom-left of a screen dropped it on exactly what you were reading. **Both come from ONE `NSEvent.mouseLocation` sample**, taken in `openWorkspaceTerminal` and passed to both helpers: two separate reads can straddle a screen or quadrant edge while the hand is still moving, and the window would then be sized for one screen and placed by the geometry of another. NB the cursor is sampled when the hotkey's async block runs, a few ms after the key went down — not at the tap itself. ⌘⌃Q runs `claude --dangerously-skip-permissions`. **The command is typed into the window by `do script` (2026-08-14), which reverses the script-file design — one process is worth more than the race it closed.** For a while the command travelled in a `/tmp/victor_claude*.sh` file passed as the shell's argv, because `do script "claude"` writes its characters into a tty whose window already has keyboard focus, so a prompt Victor starts typing in that gap interleaves and the shell runs `clahelloude`; the script also drained the tty (`stty -echo` + `while read -t 0 -k 1`) so early keystrokes couldn't land in claude's startup either. What that cost was invisible until the process tree was actually read: **Terminal runs an opened document from the window's own login shell**, so every claude window carried a permanent extra zsh — `login → zsh --login → zsh -l victor_claude.sh → claude` — for a race that needs a keystroke inside the ~200 ms the window takes to appear and announces itself immediately when it happens. Typed again, the tree is `login → zsh --login → claude`. Two consequences follow from the shell being **interactive** again: `~/.zshrc` loads, so the window cds itself to `~/workspace` (no explicit `cd` to print) and aliases exist — ⌘⌃Q still spells the flag out rather than using `cx`, purely so renaming the alias can't break the hotkey. `do script` is also **synchronous with the window's creation**, so `set bounds` follows on the next line and the old `open -a Terminal` + window-count polling loop (which existed because `open` is async and would otherwise resize the *previous* window) is gone with it. The two per-repo launchers in the Extra submenu (`openDreamClaude`) were converted the same day for the same reason. ⌘⌃T opens an empty window (`do script ""`) — there is no command to garble. NB the remaining shells in a claude window are not ours: `login -pf` is Terminal's own, and claude itself spawns a zsh snapshot at startup plus one per Bash tool call. A `zsh (kiro-cli-term)` layer used to sit in there too, from Kiro CLI's shell integration; it was uninstalled (`kiro-cli integrations uninstall dotfiles`) the same day. **Each of the three then tiles that screen** (`TerminalTiler.tile(onDisplay:)`, 0.6 s after the AppleScript returns so Terminal's own `set bounds` has settled): a window already sitting in the quarter the new one just claimed would simply be covered — the whole point of opening a second terminal is to see both. Only the display the window landed on is touched; terminals on the other screens keep their frames, because the shortcut said "make room here", not "rearrange all my monitors". NB ⌘⌃Q **shadows macOS's own ⌃⌘Q "Lock Screen"**: the `.cgSessionEventTap` sees the key first and swallows it, so the Mac no longer locks on that combination.
- **📝 Notes doc (⌘⌃N)** — opens the "notes" Google Doc in Chrome's front-window profile (`AppDelegate.notesDocUrl`, through the same `openUrlInChrome` as Gmail / Calendar, so it inherits the signed-in profile). Sibling of ⌘⌃S, which *writes* to the training notes: N is how you go and read them.
- **📕 Catalog (⌘⌃K) / 📧 Gmail (⌘⌃G) / 📅 Google Calendar (⌘⌃L)** — *(no menu rows: all three are on the ⌘⌃ cheat-sheet, which is faster to reach than a submenu and shows every key at once)* — the training `Catalog.docx` opens in Word; Gmail and Calendar open in Chrome's front-window profile (`openUrlInChrome`, so they inherit the signed-in profile). Calendar keeps its older **⌘⌥C** binding too — the event tap serves both; the menu advertises ⌘⌃L because that is the one on the ⌘⌃ cheat-sheet. The catalog answers to **K, not T**: T is the Terminal (⌘⌃T) and is used far more often mid-workshop than the catalog is.
- **✉️ TO DO mail to myself (⌘⌃M, `GmailCompose`)** — the write half of ⌘⌃G: it opens a **Gmail draft addressed to Victor, subject `TO DO`, with whatever is on the clipboard already in the body**, in Chrome's front-window profile. Nothing is sent — the draft sits in the browser so the note can still be edited, and a mail to yourself is a to-do item that survives every restart of everything. **The clipboard rides in the URL** (`view=cm&fs=1&to=…&su=…&body=…`), never through a simulated ⌘V: a paste has to guess when the compose window has loaded and which field owns the caret, and one field early writes the whole note into the To: box. A URL cannot miss, and the clipboard is only *read*, so ⌘V still works by hand afterwards. **No LLM, no API, no subprocess but `open -a "Google Chrome"`** — this is string building, which is why it is instant and works offline. The body is percent-encoded down to the unreserved characters, so a `&`/`=`/`#`/`+` in the clipboard can't end the parameter early. The whole URL is capped at **8000 chars** (Chrome would take far more, but the link also crosses Gmail's servers and a compose answering 400 is worse than a shortened one): past that the body is cut to fit — proportionally, since a multi-byte character encodes to 9, so cutting one at a time would loop tens of thousands of times — a `[…text scurtat…]` line is appended, and a bottom-left banner says so, because a truncated body doesn't *look* truncated and the full text is still on the clipboard. NB `openUrlInChrome` pulls the Chrome window onto the **built-in Retina** 1.5 s later, exactly as ⌘⌃G and ⌘⌃L do — and the Retina is what a venue projector mirrors, so mid-workshop this puts the clipboard on the wall.
- **📋 Snippet paste — Zoom link (⌘⌃Z) / email (⌘⌃E) / company details (⌘⌃R)** — `PasteSnippets` puts one of three fixed strings (Victor's personal Zoom room URL, his email address, the SRL's name + VAT code + address as a three-line block) on the pasteboard, fires ⌘V into whatever is focused, then **puts the previous pasteboard contents back** — a shortcut that helps with one line must not cost you the clipboard you were carrying. The restore waits 0.35 s rather than the 0.05 s `repasteLast` uses: a native text field has read the paste by then, a slow Electron one has not. Typing a Zoom link by hand in front of a room is slow and, being unreadable, a typo isn't noticed until nobody can join. NB **⌘⌃Z shadows whatever the focused app binds to ⌃⌘Z** (nothing standard does). ⌘⌃R (a client's finance department asking for the invoicing block, again) **took that combination off the 🔁 Restart menu item**, which is now click-only: one combination cannot mean two things, and the tap sees the key before AppKit's menu equivalent would.
- **Toggle Dark Mode (⌘⌃⌥D)** — toggles macOS dark/light mode via AppleScript
- **Mute 🎶 (auto)** — drops `🔊OS Output` device volume to 1% during Wispr Flow dictation, restores on stop. `CoreAudioManager` runs a single self-rescheduling `DispatchSourceTimer` on a serial `pollQueue`: normal cadence is 300ms; each Mouse 5 press extends a `boostedUntil` deadline by 1s during which the next ticks are scheduled 100ms apart. The Mouse 5 click handler also probes the loopback immediately (~150ms RMS/peak window, thresholds RMS 0.0002 / peak 0.0005) and — if music is playing — does a **speculative mute** without waiting for Wispr's recording state, capturing the current volume into `originalVolume` and setting `kAudioDevicePropertyVolumeScalar` to 0.01. Polls then confirm via `kAudioProcessPropertyIsRunningInput` on `com.electron.wispr-flow.*`. Restore is debounced: on Wispr `1→0` (or on a speculative mute that Wispr never confirms) we wait 1000ms of stable `recording=false` before restoring `originalVolume`; any `recording=true` read inside that window cancels the pending restore (`firstNotRecordingAt = nil`). The loopback check is **not** consulted on restore (a muted device reads silent and would falsely cancel restore). All state (`volumePushedDown`, `originalVolume`, `firstNotRecordingAt`, `boostedUntil`, `nextDeadline`) lives entirely on `pollQueue`, so reads/writes are sequential. Mouse 5 is observed via the event tap and passed through (Wispr still sees it); behavior on other triggers (right Opt-Cmd, hotkey, UI button, VAD, ESC) falls back to the boosted-or-normal poll alone. Caveats: an app crash mid-mute leaves the volume at 1% until next Wispr cycle; a manual volume-slider tweak during dictation is overwritten on restore. **Output-route guard:** the whole feature only works while the macOS default output is `🔊OS Output` (the loopback the app taps *and* whose volume it drops); if it drifts elsewhere (e.g. macOS resets to the built-in speakers after sleep), music bypasses the loopback and never ducks. On each Wispr-start edge `CoreAudioManager` reads the default-output name and, via the pure `OutputDriftPolicy`, posts a **transient native notification** ("🔇 Mute inactiv la dictare — Output = «…», nu 🔊OS Output") when it has drifted. Alerts **once per drift episode** and re-arms when a later Wispr-start sees `🔊OS Output` again (no spam). Not a permissions issue — Microphone TCC stays granted and the loopback tap still succeeds; it reads all-zero silence purely because nothing is routed through the device.
- **Re-paste (Wheel x 2)** — double-click mouse wheel re-pastes last intercepted text
- **🔎 Cmd+scroll = terminal font zoom, at a fixed window size (`EventTapManager` + `TerminalZoomSizeLock`)** — while Terminal.app or iTerm2 is focused, Cmd+scroll is eaten and turned into the native Bigger/Smaller shortcut (Cmd+= / Cmd+-), one step per wheel notch (a `zoomAccumulator` normalises notches that emit several scroll events, and resets on direction change so a reversal responds at once). Terminals answer a font change by **keeping the character grid and resizing the window** — which throws away a placement that was deliberate (tiled by ⌘⌃A, or sized to the projector), so `TerminalZoomSizeLock` **pins the frame and writes it back** after the keystrokes settle (+0.08 s, then again at +0.35 s for a lazy relayout); the terminal reflows its rows/columns into the frame instead. The frame is captured **once per gesture** (steps < 1.2 s apart are one gesture) and read/written through the in-process **Accessibility API** — same grant as `TerminalTiler`, no Automation consent, no subprocess. It must be captured **before** the keystroke is posted, so the tap thread reads it synchronously (AX messaging timeout 0.1 s so a wedged terminal can't stall the tap into a system timeout); the pid comes from `EventTapManager`'s cached frontmost app, never from AppKit off-thread. **The one non-obvious rule is drift:** the terminal snaps our write-back down to a whole number of character cells, so the window settles a few points short of what we asked for — re-reading that at the next gesture would shrink the window by a cell *every* gesture. So the settled frame is remembered, and a window still measuring exactly it counts as untouched, keeping the **original** frame authoritative; anything else (first gesture, different window, manual drag or resize) makes what's on screen the new truth. That decision is pure and unit-tested in `TerminalZoomSizeLockPolicy.frameToPin`. Only the Cmd+scroll path is pinned — typing Cmd+= / Cmd+- directly still resizes the window the way macOS intends.
- **📸 Screenshot (⌃P) — clipboard AND disk, always both** — captures the display under the cursor, puts it on the pasteboard (PNG + TIFF, so both the clip-stack poller and a CLI can read it) **and** files it as `~/Library/Caches/ro.victorrentea.macos-addons/screenshots/YYYY-MM-DD_HH-mm-ss.jpg`. There used to be two shortcuts — ⌃P to the clipboard, ⌃⇧P to the session folder — and choosing between them is a decision nobody makes correctly mid-workshop: you take the shot to paste it somewhere, and only hours later, writing the summary, discover it was worth keeping. So **⌃⇧P is gone** (VS Code gets its Command Palette back; the tap's branch now requires `!hasShift`) and there is one menu item. **The border flash is raised the instant `screencapture` exits — before the clipboard work, not after it**: re-encoding a retina capture to PNG *and* TIFF costs hundreds of milliseconds, and doing that first pushed the yellow border that far behind the keypress, which simply read as "⌃P is laggy". It cannot be raised any earlier than the capture: the flash is a real window, so anything drawn before the shot is drawn *into* the shot. **Held, ⌃P becomes the crosshair crop** (`screencapture -i`) — the tool ⌃⇧P used to reach, minus the decision: you no longer pick "full or crop" before pressing, you pick it by how long you keep the key down. **Nothing fires on the keyDown**: which of the two you meant is answered on the *release* — under `ScreenshotHoldPolicy.holdSeconds` = 0.45 s takes the screen, over it opens the crosshair (an **autorepeat** keyDown answers it earlier, so with key repeat on the crosshair appears while the key is still down; the keyUp is the fallback where repeat is off, and is the only reason `keyUp` is in the tap's event mask). The first version instead fired the full-screen shot on the keyDown, to keep a tap free of any "is this a hold?" delay — but that delay is not what waiting costs: the release costs only the length of the keypress itself (~100 ms for a tap), while firing early meant every hold took a full screen nobody asked for **and flashed a whole-screen yellow border over the crosshair already waiting for the drag**. So no shot, no border, and nothing to clean up afterwards. Esc cancels the selection, which writes no file, and nothing else runs: the clipboard and the folder are left exactly as they were. **The border a crop gets is drawn around the crop**, not around the screen (`ScreenCaptureFlash.flash(around:)`, a ring sitting entirely **inside** the region, fading inward from its edges exactly the way the screen-sized flash fades in from the screen's — so what lights up is the captured pixels themselves; drawn outside it read as a frame *around* something, which is the wrong answer to "what did I just take"): a whole-screen frame after a selection claims the wrong thing, since not taking the whole screen is what the crop was for. `screencapture` reports nothing about the region it took — the jpg carries a size and no origin — so the rectangle is reconstructed from the drag that made it (`CropDragTracker`: the cursor position when the left button went down and came back up, sampled every 8 ms off `CGEventSource.buttonState`, which is session *state* and so cannot be starved by screencapture's overlay swallowing the mouse the way an event tap would). It is then **checked against the saved file's own pixel dimensions** (`CropFlashGeometry.matchesCapture`, pure + unit-tested, with the CG→Cocoa y-flip): a space-bar window pick is a click, not a drag, and anything that doesn't line up draws **nothing at all** — a border in the wrong place is worse than no border. Two traps found by driving the whole thing with synthesized drags, both of which outlived the keyDown-capture design: two captures can be **named in the same second** and the second then overwrote the first, so every capture goes through `ScreenshotManager.uniqueURL`, which appends `-2` after the timestamp the summarizer skills parse; and a border of ours raised over the crosshair puts a window above screencapture's own selection overlay — observed to end with the selection cancelled and no file written — so a crop **suppresses** screen-sized flashes for its whole duration (`beginSuppression`/`endSuppression`) rather than only cancelling the ones already on screen. The menu carries **one** item, **📸 Screenshot (hold to crop)**: clicking it takes the whole screen (a click cannot be held) and the title is where the other half of the shortcut is taught, since a hold is the one gesture nothing on screen reveals. A second row for the crop would have been one you can never usefully click, explaining a key you already have. The file is the capture and the clipboard is a **copy of that file**, not a second `screencapture -c` run: two runs are two different moments, and the picture you pasted has to be the picture the summary can quote. **Caches, not `/tmp`, because these files must be reclaimable**: Caches is the one folder emptying the Trash, Storage Management and every cleaner tool actually reach, and macOS may purge it under disk pressure — all welcome, because the folder is a staging area, never an archive. It also bounds itself (`ScreenshotRetentionPolicy`, pure + unit-tested, pruned off the capture path after every shot): older than **14 days** or past a **2 GB** total and the oldest go, except the **newest file, which is never deleted** — that is the guard against a wrong clock throwing away the capture taken one second ago, the one about to be pasted. **The cursor's position rides in the filename** — `2026-08-14_00-34-42_at1200x500.jpg`, global CG points (y down from the primary's top, so a screen to its left gives negatives), sampled *before* the shutter since that is what `-C` draws into the picture. The shot shows the pointer but nothing in it says which display coordinate that was, and a summary reading the folder months later cannot recover it. The same point is marked **on screen** for ~2 s by the minigun's red aiming reticle at half its aiming size (`ScreenCaptureFlash.markCursor` → `EmojiAnimator.makeSniperReticle`), at **80 % opacity from the first frame** with the only fade in its last quarter: a mark that fades *in* asks to be watched arriving, and this one is already there when you look. It **zooms out** as it lands — in at 1.3×, settling to 0.9× over 0.35 s — so it reads as a scope being brought down onto the spot, and what stays behind is the smaller, quieter mark rather than the loud one that arrived. The border says what was captured; this says where you were pointing while the transcript recorded what you were saying about it. Three things IINA does *not* do correctly on its own, each fixed here after being watched misbehave: **(1) which screen** — the clip must land on the **built-in Retina whatever macOS calls the main display**, because the Retina is what a venue projector mirrors while at a venue the *ASUS* is made primary (`DisplayArrangementManager`), so "main screen" is exactly the wrong answer there. mpv's `--fs-screen` is **ignored** (verified: IINA manages its own `NSWindow`), so the window is launched *windowed*, moved onto the Retina through the **Accessibility API** (same in-process grant as `TerminalTiler`, no Automation consent) and only then fullscreened via `AXFullScreen` — in that order, because a fullscreen window can no longer be moved between displays. Two traps: IINA exposes **several AX windows and the first is not the player** (a 1728×37 `AXUnknown` strip whose `AXFullScreen` isn't even settable — writing frame + fullscreen there silently did nothing while looking like success), so `playerWindow(among:)` picks the largest **`AXStandardWindow`**; and the fullscreen request is **repeated until the attribute reads back true**, since IINA puts a window up before it can be fullscreened and an early write is accepted and ignored. The Cocoa→AX coordinate flip (y **up** from the primary's bottom vs **down** from its top — identical only for the primary screen, i.e. everywhere except the venue layout) is pure and unit-tested in `VideoPlayer.axFrame(screenFrame:primaryTopY:)`. **(2) nothing plays next, ever** — IINA loads the *containing folder* as a playlist, so a finished snippet rolled straight into the next file in `videos/` on the projector (observed: "Papaguera" → "Feel it coming"); neither `playlistAutoPlayNext=0` nor `--mpv-autocreate-playlist=no` stopped it, so the clip is played from a **staging folder holding exactly one file** (`videos/.play/`, a **hardlink** — not a symlink, precisely so resolving it can't lead back to the folder full of siblings — rebuilt per play). Verified by `playlist-count: 1`. **(3) the end of a clip rewinds and pauses** — with `--mpv-keep-open=yes` mpv freezes on the last frame, which leaves a still on the projector and needs a seek before it can be replayed, so the player is watched over **mpv's JSON IPC socket** (`--mpv-input-ipc-server`, `MpvIPC`: one connection per command, every failure = nil) and told to seek back to the snippet's start second and pause the moment it reports `eof-reached` — leaving it primed so **SPACE replays the clip**. Resuming re-arms both the watch and the auto-kill, so a replay gets a full 60 s of its own instead of being cut off by the first play's deadline. `GET /video/stop` closes it. Headless hooks: `GET /test/video/<id>` (play at the manifest second) and `GET /test/video/stop`. **Local clips (no YouTube id) are supported too** — a manifest entry may carry a `thumb` (base64 JPEG, extracted with `ffmpeg` and served inside `GET /videos`) instead of relying on `img.youtube.com/vi/<id>`, with a made-up id as its key (`fearLocalClip`, `papaguera`). Those are added by hand (copy the mp4 into `videos/`, grab a frame, upsert the entry); the `add-training-video` skill only covers YouTube URLs. **Strip any baked-in letterbox before adding a clip** (`ffmpeg -vf cropdetect` to find it, then `crop=`): black bars inside the file are not black bars the player can remove, and they stack with the aspect-ratio bars on screen — Papaguera arrived as 640×480 with only 640×344 of picture, i.e. 28% of the frame was baked-in black.
- **🔌→🤖 Tablet app auto-deploy on USB (`AndroidAppDeployer` + `AndroidDeployPolicy`)** — plugging the tablet into the Mac rebuilds and reinstalls the **LaunchBreak Android app** when the tablet is carrying an older build. The tablet is deployed to by hand between workshops, so it drifts behind the Mac add-on it talks to (new sounds, new tiles, a changed protocol) and nothing says so until something misbehaves in front of a room; the cable going in is the one moment the Mac can fix that itself. The trigger is `UsbTunnelKeeper.onTunnelArmed` — the **armed** edge, not the raw IOKit attach, so adb is already answering (the two share one `UsbTunnelKeeper.adbPath`, hence one adb server). **"Behind" is a source stamp, not a version:** `versionName` never changes and a rebuilt APK hashes differently every time (zip timestamps), so the Mac stamps the *sources* — the HEAD commit when the tree is clean, plus the newest edit's timestamp when it is dirty (so every uncommitted save deploys on the next plug, while ten plugs after a no-op pull deploy nothing) — and, **only after a successful install**, `adb push`es that stamp to a marker on the tablet (`/sdcard/victor-launchbreak-deploy.stamp`, on `/sdcard` rather than in the app's data dir so it survives the reinstall it describes). A **missing** marker deploys once, deliberately: what's on the tablet is then unknown, and assuming it's current is the expensive mistake. The gradle build runs **only after** the stamp says so, so the common case (cable in to charge, sources unchanged) costs one `adb shell cat` — no build, no reinstall, no app restart, no notification. On a deploy: `./gradlew assembleDebug` → `adb install -r` → best-effort `pm grant WRITE_SECURE_SETTINGS` + `settings put global audio_safe_volume_state 0` (keeps Android's headphone-safety dialog off the soundboard) → **force-stop + relaunch** (`install -r` leaves the old process running the old code) → write the marker. **`JAVA_HOME` is resolved, never assumed** — a LaunchAgent-started app inherits almost nothing, and AGP 8.7 runs on JDK 17–21 while this Mac also has 22–25 installed, so the candidates are `VICTOR_ANDROID_JAVA_HOME`, sdkman's `current` (what Victor's own shell builds with), then `java_home -v 21/17`. Both outcomes raise a **native macOS notification** (`AppDelegate.postAndroidDeployNotification`): `Android app updated to version` / `4 Aug 2026, 19:41 · a1b2c3d`, or `Android app update FAILED` naming the step — a deploy that failed silently is worse than one that never ran, since the tablet then keeps the old build while Victor believes it's current. A stamp that just failed is not retried for 10 min (a broken build fails the same way every time), and an `inFlight` flag collapses replug bursts. **A freshly plugged cable is given 8 s to settle before the deploy starts, and `adb install` gets 3 attempts 4 s apart** — the very first deploy this ever ran began 3 s after the armed edge and its install died mid-transfer while the USB tunnel re-armed underneath it, which is precisely the manual replug this feature exists to remove. The command runner also **joins its output reader** instead of sleeping "long enough": the truncated tail is exactly where the reason a command failed is written (that install reported only `failed to install …:`, cause cut off). Decision + wording are pure and unit-tested in `AndroidDeployPolicy`. **Accepted caveat:** a deploy **restarts the tablet app**, so a mid-workshop replug *with moved sources* blinks the LaunchBreak UI — gating that on "not during a session" would mean the deploy never happens on the day it matters. - **📱→🤖 Phone low battery mirrored to the tablet (`PhoneBatteryMonitor` + `PhoneBatteryPolicy`)** — when Victor's **phone** (not the Mac, not the tablet) is nearly flat, the tablet blinks a phone-in-a-rounded-square mark slowly red in the top-left of its action bar, above the tiles, until the phone is back on a charger. macOS *already* warns about this — Soduto, the KDE Connect client, posts a "Low Battery | <phone>" notification — and that notification is precisely the one that gets missed: it lands on the screen being projected to the room, or behind a fullscreen deck, while nobody is looking at the Mac. The tablet is in eye-line all day, so the warning is doubled there. **The notification IS the state machine, which is why it is the source and a percentage isn't.** Soduto keeps the peer's battery status purely in memory (`BatteryService` builds no menu item, writes no preference, exposes no API — nothing outside the process can read it), but what it *does* publish behaves exactly the way Victor asked: it posts the notification on the phone's low-battery threshold event, **re-delivers it with the fresh percentage on every subsequent battery packet while the phone stays low, and removes it the moment the phone reports charging**. So presence of the notification is the warning and "until you plug it in" comes for free — we never track charging ourselves. Mechanically the Mac reads macOS's own notification store (`~/Library/Group Containers/group.com.apple.usernoted/db2/db`) every 30 s, matching `app.identifier = com.soduto.soduto` (lowercased there, unlike the bundle id) **and** an `NSUserNotification.identifier` starting with `com.soduto.services.battery` — the identifier, not the localized title, is what separates a battery notification from Soduto's pairing / share / SMS ones. The store is **WAL-mode SQLite and is copied aside before it is read** (`db` + `db-wal` + `db-shm` → a temp folder, queried, deleted): a read-only connection to a WAL database still needs to write the `-shm` index, and skipping the `-wal` would be cheaper and wrong — the newest notifications are exactly the ones still sitting in it. The reading rides to the tablet on the existing `/ping` (`phoneBatteryLow` + `phoneBatteryPct`); the blinking itself lives entirely on the tablet. **Two guards.** A notification nobody has refreshed for **90 min** stops warning (`PhoneBatteryPolicy.staleAfter`) — a phone that goes flat and switches off never sends the charging packet that would clear it, and would otherwise blink the tablet forever; while the phone is genuinely connected and low it drains fast enough that packets keep arriving well inside that window. And the tablet clears the mark whenever the Mac link drops, since it is the Mac that decides when the warning is over. **Requires Full Disk Access** — the only thing in this app that does, and it is not granted by default; the first denied poll raises a native notification saying so, because a feature that silently never fires is indistinguishable from a phone that never runs low. Decisions are pure + unit-tested in `PhoneBatteryPolicy`, and `PhoneBatteryMonitorTests` runs the real query against a fabricated store built with usernoted's schema. Test hooks: `GET /test/phone-battery`, `GET /test/phone-battery/simulate/<pct>`.
- **🖥️ Auto display arrangement (projector workflow, `DisplayArrangementManager`)** — reshapes the displays automatically when a projector / room TV is plugged in or out, so Victor never re-does the venue setup by hand. Detection is `CGDisplayRegisterReconfigurationCallback` (fires on every hot-plug / mode / mirror change), **debounced ~1.2 s** so the hardware settles before we read + apply; the fix is **attempted only once per change** — we act only when the *scene* — `(hasProjector, hasASUS)` — actually changes, so if the set of monitors doesn't change there are **no further layout/mirror changes** (a manual re-layout Victor makes afterwards is left untouched). No self-loop: our own `CGCompleteDisplayConfiguration` callbacks compute the same scene and no-op, plus an `isApplying` guard + 1 s cooldown. Roles are resolved **live, not from a frozen profile** (works with any venue's projector, different EDID each time) and consult the persisted **`KnownDisplays`** ("mine") set: built-in = **Retina** (`CGDisplayIsBuiltin`); `NSScreen.localizedName` contains "ASUS" = the **ASUS MB166C** travel monitor; any **other known** external (home monitors / TV, added via "Trust current external displays") = a plain extended desktop that is **never mirrored and never disturbed**; anything else external = an **unknown = venue projector / room TV**. Two apply scenarios when an unknown external connects: **(1) projector + ASUS** → the projector *mirrors* the Retina at **1920×1080** ("what's projected to the room"), the **ASUS becomes primary/main** (origin `(0,0)`) on the right, Retina extended to **its left** (origin `-1920,0`); **(2) projector, no ASUS** → the projector simply *mirrors* the Retina (also dropped to 1920×1080), Retina stays main. **Unknown external unplugged** → revert to the standard rig: Retina **main** at its native mode, ASUS (if present) extended to the Retina's **right**. **At-home guard:** if a *known* non-ASUS external (home monitor / TV) is connected we assume Victor's own multi-display layout is set the way he wants and **auto-arrange keeps hands off entirely** (the manual force still overrides) — this also stops a home TV from ever being mirrored at 1080p. Applying is **two Quartz transactions**: phase 1 = display modes + mirror topology (`CGConfigureDisplayWithDisplayMode` + `CGConfigureDisplayMirrorOfDisplay`), phase 2 (~0.6 s later, its own `CGBegin…/CGComplete…`) = origins (`CGConfigureDisplayOrigin` — who is main, who sits where). No external tools, **no Screen-Recording permission** needed. The Retina's user-normal (native HiDPI) mode is captured the first time we observe a projector-free state and restored verbatim on revert. 1080p is found via `CGDisplayCopyAllDisplayModes` + `kCGDisplayShowDuplicateLowResolutionModes`, preferring a true non-HiDPI 1920×1080 @ 60 Hz. It **does not auto-apply on launch** (only on subsequent changes) so starting the app never reshuffles a happy layout; the menu item **🖥️ Arrange Monitors** (top-level) and `GET /test/projector` force it on demand. On each applied change it flashes an **immediate** (not presence-gated) bottom-left `StatusBanner.showNow` for 8 s describing the new layout (e.g. "🖥️ Projector: mirror + ASUS primary"). ### whisper-transcribe
Live dual-channel Whisper transcription engine (extracted from training-assistant daemon):
- **WhisperTranscriptionRunner** — captures audio from 2 sources, transcribes via mlx-whisper on Apple Silicon GPU
- Writes `[HH:MM] Speaker: text` lines to per-day files in `TRANSCRIPTION_FOLDER`
- Default devices: XLR mic (device 5) + Zoom loopback (device 17)
- Auto-detects Romanian/English, filters hallucinations, RMS-based silence skipping
- Queue-aware batching merges adjacent same-speaker chunks before inference; default wait budget is tuned for non-live subtitle use
- Adaptive quality can switch to a faster Whisper model when transcription backlog grows, then return to balanced quality when queue drains
- Startup guard: `WHISPER_PARENT_PID` is mandatory; runner exits early if missing/invalid (prevents unmanaged launches)
- Parent sentinel thread exits whisper when Swift parent dies; combined with Swift-side pre-start cleanup to reduce stale/orphan runners during automated app restarts

**PortAudio discipline (2026-07) — one root cause behind both the crashes and the silence.** `_portaudio_reinit()` is `Pa_Terminate()`: **process-global**, it closes *both* channels' live streams. Three rules keep it from tearing the app apart, all learned the hard way:
1. **Only reinit when the device set actually changed** (`_device_set_changed()`, read from CoreAudio — asking PortAudio would need the very reinit we're avoiding; errors answer "yes", since a needless reinit is survivable and missing a hot-plugged mic is not). `_check_best_device` used to call it unconditionally, so *every* device check killed two healthy streams.
2. **Never touch PortAudio on CoreAudio's notification thread.** The ctypes listeners invoke the handler directly, so `_on_device_list_changed` now just sets an `Event` and a `device-check` worker does the work — it also **coalesces**, because one dock/projector plug fires the listener once per input device and each of those used to spawn its own teardown. The old code slept 2 s and then called `Pa_Terminate()` right there while CoreAudio held its locks; the crash reports show exactly that, as a double-free on the `HALC_ProxyNotification Call Listener Queue`.
3. **`self._pref_watch_mtime` is seeded from the file's real mtime**, not `0.0`. Starting at `0.0` meant the preference watcher's first poll *always* reported a phantom change — a fake source switch ~1 s into **every single run**, which detonated PortAudio underneath two streams that had just opened. That one line produced the paired `Invalid stream pointer [PaErrorCode -9988]` on every start (85 in one day's log) and the SIGABRT double-frees.

**Threads must never die quietly.** A capture thread that dies is invisible from outside: the process lives, the *other* channel keeps working, the PID is healthy, the icon says 💬 — and nothing is transcribed. That happened because `_loop`'s error handler called `self._resolve_fn()` **unguarded inside an `except` block**; an exception there is not caught by its own `try`, so it escaped and killed the thread. Only the Victor channel has a `_resolve_fn`, which is why only Victor's thread ever died. Now: that call is wrapped, both `_loop` and `_transcriber_loop` run under `_supervised_*` wrappers that log and restart on anything (including `BaseException`), threads are **named**, and a `threading.excepthook` routes any remaining escape into our own log.

**Quiet crashes (no "Python quit unexpectedly" dialog).** The interpreter is `Python.app` — a bundled GUI app — so a fatal signal used to put a modal crash alert on the projector mid-talk. `_install_quiet_death_handlers` installs libc's `_exit` as the C-level SIGABRT/SIGSEGV/SIGBUS handler (async-signal-safe; a Python handler would deadlock, since SIGABRT from libmalloc arrives holding the malloc lock), so the process dies by *status* instead of by uncaught signal: no crash report, no dialog. **The trade-off is real — we lose the `.ips` file.** `faulthandler` cannot rescue it: it refuses to `register()` fatal signals ("use `enable()` instead") and `enable()` re-raises with the DEFAULT action rather than chaining, which is the dialog again. What replaces it: everything Python logged on the way down, the thread hook above, and `WhisperProcessManager`'s termination handler, which now decodes the status (`6` = SIGABRT/likely PortAudio double-free, `10` = SIGBUS, `11` = SIGSEGV) into an `overlayError`. Set `WHISPER_QUIET_CRASH=0` to get crash reports back. SIGTERM/SIGINT also get a handler that stops the runner and `os._exit(0)`s, skipping CPython's shutdown — which is where `atexit` would otherwise tear PortAudio down with callbacks still live. (The parent sentinel has always used `os._exit`, which is why it never crashed.)

**Whisper's stderr is decoded incrementally.** `WhisperProcessManager` used to drop the **entire** pipe buffer when `String(data:encoding:.utf8)` returned nil — and whisper's output is emoji-dense, so a chunk regularly ends mid-codepoint. That is how a Python traceback explaining a dead capture thread could vanish without a trace. Partial tails now carry over to the next read and no buffer is ever discarded.

`GET /sound/pressed/<file>` and on every stop `GET /sound/stopped/<file>` (bare
filenames), and the Mac looks the effect up in `SoundEffectMap.swift` — the
single source of truth (`onPress: [file → effect]`, `onStop: [file →
effect/stop]`) — then dispatches through the existing `onEffect` switch (reusing
all BT visual-compensation/sync logic). **Changing a mapping or adding a new
effect needs only a Mac rebuild — no tablet redeploy.** The siren
(`02_siren.mp3`) is the one exception: it drives the alarm overlay
(`/alarm/start`,`/alarm/stop`) and stays special-cased on the tablet. Effects
are CALayers on the overlay's `hostLayer`, animated via `CAKeyframeAnimation`
on `contents` from bundled gif frames (`Bundle.module`).

**Lifecycle rule (2026-07): every overlay effect MUST self-terminate at its
sound's length — network stop messages are an optimization, never the only
teardown.** The tablet's `/sound/stopped` → `onStop` chain (and even the
pre-press `/effect/stop-all`) is best-effort: on a flaky venue network the
tablet falls back to the Railway relay and those GETs get lost, which used to
leave looping overlays (star-wars, brother, gangnam, drum-roll) on the desktop
forever. Every `show*` therefore schedules its own authoritative stop —
`trackEffect(duration:)` for one-shots, or an explicit
`asyncAfter(realMp3Duration + 0.3s grace)` for loopers, reading the paired
mp3's length via `AVURLAsset` — **in the silent (`playSound: false`) tablet
path too**, since that's the path real presses take. Self-stop timers are
**identity-guarded** (`activeEffects[key] === layer`, the love-hands pattern)
so an old run's timer can never kill a newer run of the same effect. The one
deliberate exception is the siren's alarm overlay (an unbounded toggle — its
sound loops until explicitly stopped). When adding a new effect, follow this
rule from the start.

  happens, which is the one moment it must be unmistakable; the wedge passing
  *behind* it now reads as the thing that revealed it. Each detection also
  **zooms it in**: it lands at **2×** and settles to its own size over **1 s**,
  cubic-ease-out so the motion is spent in the first third (it arrives, it
  doesn't creep). The zoom is sampled on the **same keyframe grid and the same
  `detT[di]`** as the opacity flash, so it starts on the exact frame the 💩
  becomes visible; between detections the scale is parked back at 2× ready for
  the next one, and that 1×→2× reset is placed **after** the fade has fully
  finished (`coverT + fadeT`) so it always happens at zero opacity and can never
  be seen. The rotation is **keyframed** (not constant): ~0.5s beep-free
  lead-in, then the front sweeps over the 💩 on **three radar beeps** in the clip
  (clip times 0.104/2.211/3.879s; one full turn between detections). The Mac
  **owns the audio** here — `showSonar(playSound:true)` plays `23_radar.mp3`
  delayed (`soundStartRel` + 0.1s) so the beeps land on the three detections; the
  effect ends (fading out **while still rotating**) the moment the 3rd detection's
  1s fade finishes, so the front never sweeps the 💩 a 4th time unshown. Pure
  formatting/timing is derived up-front from `beepClip`/`detT`/`animEnd`.

  `SoundEffectMap`** (the press path would otherwise double-trigger it). `/test/sonar`

### Tablet ↔ Mac transport (local Wi-Fi preferred, internet last resort)
The tablet reaches the Mac over four transports, first that answers wins (`MacLink.reach`,
tablet side): USB (`localhost:55123` via `adb reverse`) → **the Mac's raw LAN IP `http://<ip>:55123`**
→ mDNS (`Victor-Mac.local:55123`) → the **Railway relay** (`RailwayBridgeClient` ⇄ tablet's
`MacBridge`, `wss://interact.victorrentea.ro`), which is a genuine LAST resort. The `/ping`
response advertises the Mac's own LAN IPv4s as **`macLanIps`** (`NetworkInfo.lanIPv4Addresses()`,
`en*` interfaces) so the tablet — which gets `/ping` even over the relay — can probe the Mac
**directly on the shared Wi-Fi**, sidestepping mDNS (which phone hotspots filter). This is what
stops the tablet falling to the internet relay when both devices are on the same hotspot.
The `TabletHttpServer` `NWListener` already binds all interfaces, and the tablet's
`network_security_config` permits cleartext to those raw IPs (previously only `.local`/localhost,
so the raw-IP path was silently blocked).

### Tablet sound routing (tablet → Mac playback)
The Android LaunchBreak tablet pings `GET /ping` every 5s (response carries `soundsHash` +
`macLanIps`; see the transport section above).
When the tablet has no BT speaker / wired headphones and the Mac answers, the tablet routes
soundboard playback here instead of playing locally:
- `GET /sound/play/<file>?vol=<0-100>` — one sound at a time, a new play preempts the
  current one; responds `{ok, durationMs}` (the tablet schedules its effect-stop chain from
  it); 404 for unknown files → tablet falls back to local playback
- `GET /sound/stop`; `/effect/stop-all` also stops the tablet-routed sound
- `GET /sound/volume/<pct>` — live player-level volume (never the macOS system volume)
  + plays `click.wav` (the tablet's generated 1800Hz tap) at the new level as feedback
- Watchdog: the routed sound is stopped if pings cease >12s (tablet crash / network drop)

**Anti-drift**: `Sources/VictorAddons/Resources/sounds` is a single folder symlink to
`victor-android/app/src/main/assets` (the canonical sound library; dereferenced into the
bundle by `build-app.sh`), so the protocol identifies sounds by bare filename.
`SoundsManifest` hashes every bundled mp3 (SHA-256, canonical "name:hash\n" lines);
`GET /sounds/manifest` returns the per-file map. A hash mismatch in `/ping` means a stale
Mac bundle — the tablet plays the differing files locally and shows an amber dot until
`build-app.sh` is re-run.

**BT wake-up compensation — tablet-adjustable (header slider).** When the **Mac's own** default output is a Bluetooth speaker, the add-on prepends a short (near-)silent "wake" tone before every sound + paired animation so the A2DP amp is spun up and the start isn't clipped (see `BluetoothOutput` / `SoundTimingConfig.currentBluetoothCompensation`). The duration is a **`SeekBar` in the tablet's action-bar header** (`menu_bt_comp.xml`, range `0.00s`–`1.20s` in **50ms steps**, with the name and the value as **one caption stacked above the slider** — `BT wake: 0.9s` — rather than a label on its left and a readout on its right: the header row is starved for width while its vertical space is free, so stacking gives back ~100dp for free). The tablet **owns** the value: persisted in SharedPreferences (`mac_bt_comp_ms`), seeded the first time from the shared `sound-timing.json` `macBluetoothCompensationMs` (currently 800ms — i.e. "the current one in the add-on"), committed **on finger-lift** and pushed to the Mac via `GET /bt-compensation/<ms>`, and **re-pushed on every (re)connect** (`onMacLinkStateChanged` false→true edge) because the Mac resets to its file default on restart. `macBtCompMs` is seeded **before `macLink.start()`** so that first connect-edge push carries the persisted value, not the field default. On the Mac, `SoundTimingConfig.setBluetoothCompensation` stores a runtime override (clamped `0…1.2s`) that wins over the file default; it is **not** persisted on the Mac (the tablet is the source of truth). The slider lives as a **menu action item** (like the volume wedge), not in the custom title view, because the toolbar clips trailing children off the title view; the three 100dp header spacers were removed to make room (route indicators + one-line title preserved).

## Deployment
- **App bundle**: `./build-app.sh` creates `/Applications/Victor Addons.app` (Spotlight-searchable)
- **LaunchAgent**: `./install-startup.sh` symlinks plist, loads LaunchAgent for login auto-start
- Re-run `build-app.sh` after changes to `start.sh`, icons, or app identity
- `start.sh` exports `VICTOR_ADDONS_ROOT` so the app can resolve `whisper-transcribe/whisper_runner.py` reliably when launched from `/Applications` bundle.

**Operational note (2026-04):** To avoid repeated Accessibility re-prompts across deploys, app builds should be signed with a stable identity. `build-app.sh` auto-detects and uses `Victor Addons Local Code Signing` from `login.keychain-db` when available (or `CODESIGN_IDENTITY` if set), otherwise falls back to ad-hoc signing.

**Operational note (2026-04):** On app launch, Accessibility is checked without forcing a system prompt (`AXIsProcessTrusted()`). Missing permission is reported in-app; prompting/opening System Settings should be user-initiated.

**Operational note (2026-05):** Single-instance lock + uniform launch behavior:
- `/tmp/VictorAddons.pid` lock with `proc-name` verification before SIGTERM (avoids killing unrelated PIDs after a stale PID file from a hard crash).
- SIGTERM is delivered via `DispatchSource.makeSignalSource` (not raw `signal()`), so the handler can call `AppDelegate.tearDownForReplacement()` which `SIGKILL`s the Whisper subprocess synchronously. Previous design left whisper orphan until its parent-watch sentinel noticed (up to 2s).
- New-instance grace timeout extended from 200ms to ~1s before falling back to SIGKILL on the previous instance.
- On launch, if stderr is not already a regular file (i.e. not piped by `start.sh`), `main.swift` redirects stdout/stderr to `/tmp/victor-macos-addons.log` itself — so launching via `open` (Spotlight, Login Items) logs to the same file as a LaunchAgent boot.
- Result: `pkill -f "Victor Addons"; open "/Applications/Victor Addons.app"` and `launchctl kickstart -k gui/$UID/ro.victorrentea.macos-addons` are now behavioral equivalents.

**Operational note (2026-07): clicking the app again replaces it (`AppRelaunch`).** The hand-over above was always correct — and almost never ran. LaunchServices treats `open` of an already-running bundle as an **activation, not a launch**: no second process starts, so nothing ever writes a new pid, and clicking "Victor Addons" in Spotlight while it was wedged did *precisely nothing*. The only way out was `pkill` in a terminal. Two entry points now close that from the other side, both funnelling into `AppRelaunch.relaunch`:
- `AppDelegate.applicationShouldHandleReopen` — the reopen event macOS *does* deliver to the running instance. For a menu-bar app with no windows, "I opened it again" only ever means "give me a fresh one". Reopens within 5 s of launch are ignored (AppKit can deliver one as part of our own launch; restarting on that would loop).
- ~~the 🔁 Restart menu item~~ — **removed 2026-08-14**: reopening the app *is* the gesture you reach for when something is wedged, so the row was a second way to say it. `applicationShouldHandleReopen` remains the whole story.

The relaunch is performed by a **detached `/bin/sh` helper**, not by us, because the one thing that must survive is the relaunch itself: it polls until our pid is gone (10 s ceiling, then launches anyway) and only then runs `open -n`, so it behaves identically whether we exit cleanly, are SIGKILLed, or crash on the way out. `-n` forces a genuinely new process even if LaunchServices still counts the dying one as running. The target path travels in the **environment, not argv**, so the helper's command line never contains "Victor Addons" — otherwise the deploy habit of `pkill -f "Victor Addons"` would kill the very helper meant to bring the app back. We then `tearDownForReplacement()` (SIGKILLing whisper) and `exit(0)`, so the new instance inherits a Mac with no orphan fighting it for the microphone. A re-entrancy flag collapses a burst of reopen events into one helper; a failed spawn leaves the old instance up rather than killing it with nothing to replace it.

**Operational note (2026-06):** `TerminalTiler` reads/writes Terminal window geometry through the in-process **Accessibility API** (`AXUIElement`), relying only on this app's own Accessibility grant (the same one behind the global event tap). It previously shelled out to `osascript` + "System Events" UI scripting, which needs a *separate* Automation (Apple Events) grant; after a re-sign that grant's stored code requirement no longer matched the running binary, so the Apple Event blocked on a consent prompt a headless `osascript` subprocess can't surface and tiling silently hit the 5s timeout (symptom: `AppleScript failed: Timed out after 5.0s` in the log; ⌘⌃A and the menu item both no-op). The AX path needs no Automation permission and never spawns a subprocess.

**Shortcuts/menu (2026-06):** The 🔥 menu item is **Whip Agent** (briefly just "Whip"; formerly "Whip Claude"), bound to **⌃W** globally (event tap, suppressed) and shown as ⌃W in the menu. NB ⌃W globally shadows the usual "delete word backwards" in terminals/editors. The bottom-left notification pill (`BottomLeftBanner`) renders the hover-hint chip ("Hover to undo/snooze/continue/Send") **pinned to the pill's bottom-left corner** (fixed — no longer riding/moving), with the **orange countdown bar filling the region to the right of the chip** (from the chip's right edge to the pill's right edge) left→right. Countdown banners are floored at **30% of the screen width** (`countdownMinWidthFraction`) so the fixed chip and the bar to its right always fit; plain (non-countdown) banners still hug their text. Reusable across every banner caller.

**Menu (2026-08-14) — the menu is not a second cheat-sheet.** Holding ⌘⌃ draws every one of this app's ⌘⌃ shortcuts on the secondary screen at once (`KeymapOverlay`), which is faster than opening a menu and walking a submenu — so rows whose only content was "this key exists" were removed: **📕 Catalog** (⌘⌃K), **📧 Gmail** (⌘⌃G), **📅 Calendar** (⌘⌃L), **Tile Terminals** (⌘⌃A), **Terminal in workspace** (⌘⌃T), **🎅 workspace (plain)** (F8) and the two greyed-out reminders (⌘⌃V *Paste Emotions*, ⌘⌃S *Selection to Notes*). Every one of those keys is still bound in `EventTapManager` — only the rows are gone, and `MenuBarManager.onOpenCatalog` / `onOpenGmail` / `onOpenCalendar` survive as the tap's landing points. **🔁 Restart** went too (reopening the app relaunches it). **`🎅 workspace` was broken**, not redundant: it opened claude in `~/workspace/ai`, a folder that became `skills-private` and no longer exists. What the Extra submenu keeps is what no key replaces: **📝 Paste Clipboard to Notes** (a menu click cannot capture the previous app's selection, so ⌘⌃S has no menu form at all), the **Emoji Overlay** and **Dark Mode** toggles, and the two per-repo claude launchers (each opens claude in a named repo, renamed, in its own screen quarter). The 🔥 item reads **Whip Agent**, and **📸 Screenshot (hold to crop)** is one row teaching both halves of ⌃P.

**⏱️ Resumed — the row that colours (2026-08-14).** "⏱️ Resumed 1h 51m ago" turns **yellow past 1h15m** and **red past 1h45m** (`RHTimerMonitor.urgency`, pure + unit-tested; thresholds are Victor's teaching rhythm — a section runs about an hour and a quarter, and past an hour and three quarters the room is gone). The row is read at a glance mid-sentence, so the colour has to carry it: by the time you have *read* "1h 52m" you have spent the attention the glance was meant to save. It is drawn through `attributedTitle` because the item is **disabled** — a readout, nothing to click — and AppKit dims a disabled item's plain title, which is the opposite of what a warning wants; an explicit foreground colour survives that dimming. The yellow is appearance-resolved like the menu-bar apple glyph (`systemYellow` reads on a dark menu and vanishes on a light one, so light mode gets a dark amber). The ⏱️ moved into `RHTimerMonitor.formatElapsed` itself, so the row no longer changes shape the moment it starts saying something.

**Notes banner — the pill carries the notes marker (2026-08-14).** Both bottom-left notes pills now open with the very emoji their line will carry in the notes file, straight off `SessionNotesAppender.Marker` (one source, so the two can't drift): an **intercepted agent prompt** shows as `🤖 <text>` and an **intercepted / hand-sent text** as `📋 <text>` — the latter replacing the word `Pasted:`, since the mark is recognised faster than the word and it is the same mark the reader will meet again in the notes list a moment later. Previously the prompt pill had no prefix at all and the paste pill spelled its verb out, so at a glance the two flows were the one thing the pill didn't say — which is exactly what the markers were introduced to disambiguate in the file itself.

**Notes banner — outcome-flavored exits (2026-06):** Every *interactive* bottom-left pill ends one of two ways, and the exit animation tells the user **which**, so the gesture and the feedback match:
- **`dismissRisingFade()` — accept / commit.** The pill (and its hint) float straight up ~140px while fading over **~1s** (`.easeIn`), as if the text lifts off into the notes. Used when you **hover-confirm "Send prompt to notes?"** and when a paste's undo window **lapses un-hovered** (it stuck).
- **`dismissSinking()` — cancel / say "no / stop".** The pill (and its hint) slide straight **DOWN** off the bottom of the screen over **~0.7s** (`.easeIn`, no fade — it's anchored at the bottom edge, so dropping it past its own height carries it fully out of view), the mirror image of the rising "accept". Used when you **hover-to-undo a paste** and when you **hover-to-snooze the 😶 silent-transcription warning** (`SilentTranscriptionWarning.snooze`) — in both cases the downward motion alone reads as "dismissed / put away".
- Wiring lives in `SessionNotesAppender`: a banner-free **`writeNotes`** core feeds both entry points (`pasteAndOfferUndo` for keypress pastes, the `offerPrompt` hover handler for prompt-capture); **`performUndo` returns `Bool`** so the caller sinks the pill *only* when the undo actually landed. The old `"↩️ Undone"` / `"pasted in notes"` text flashes are gone — the animation **is** the feedback. The hover-approve window itself is `hoverActionDuration` (**7.5s**). The notes flows and the silent-warning snooze use the rising/sinking pair; status banners still use plain `dismiss()`.
- **A parked cursor is not a decision (`HoverMotionGate`).** The 2 s hold that fires `onHover` used to require only that the cursor be *inside* the pill — and the pill sits in the bottom-left corner, exactly where a hand naturally leaves the mouse, so a prompt sent itself to the notes (or a paste undid itself) with nobody touching anything. The dwell now also requires the cursor to keep **moving**: in every **0.5 s slice** it must travel at least **4 pt** (rolling anchor, so a slow continuous drag counts as well as a jiggle; 1 px trackpad jitter does not). A slice with no movement **zeroes the dwell progress** — the whitening/nudge visibly falls back to rest — and the gate re-arms, so moving again rebuilds it from zero. Motionless = never fires, however long the cursor stays. The rule is pure + unit-tested in `HoverMotionGate`; `BottomLeftBanner.tickHoverDwell` is the only caller.

## AI Instructions
- After any significant design, architecture, or deployment change, proactively offer to save the decision to memory for future conversations.
- After any code change in this project, always: push to master (`git push`), run `./build-app.sh`, then restart the app (`pkill -f "Victor Addons"; open "/Applications/Victor Addons.app"`).
- **Testing during a live workshop is fine — don't hold back.** Victor doesn't mind app restarts or transcription gaps mid-session. The only constraint: the **built-in retina display is what's projected to the room**, so do any *visual* testing (overlays, screenshots) on the **right-hand external screen** instead — never put test UI on the projected retina display.
